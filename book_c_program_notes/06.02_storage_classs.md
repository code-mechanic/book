```text
+-------------------------+------------------+-------------------------+---------------+
| storage class /         | scope            | life                    | default value |
| specifier               | (range)          | (alive or dead?)        |               |
+-------------------------+------------------+-------------------------+---------------+
| auto                    | with in body     | with in body (alive)    | GV            |
| static                  | with in body     | entire Program (alive)  | 0             |
| extern                  | entire Program   | entire Program (alive)  | 0             |
| register                | with in body     | with in body (alive)    | GV            |
+-------------------------+------------------+-------------------------+---------------+

Note: 'GV' stands for Garbage Value.

`Scope` is subset of life. If variable is dead then there is no meaning of checking
`range` (accessibility)
```

This table is the master key to how the C compiler manages physical memory. By changing a variable's storage class, you are explicitly commanding the compiler to move it to a different segment of your microcontroller's architecture.

- **`auto` (The Stack):** Because its life is restricted to "within body", the compiler places `auto` variables on the **Stack**. When the function is called, the stack frame is pushed, and the variable is created containing whatever residual 1s and 0s are at that RAM address (Garbage Value or 'GV'). When the function returns, the stack frame pops, and the variable is destroyed.

- **`static` (DS / BSS):** This is a crucial tool for embedded state machines. The table shows its scope is restricted to "within body" (so other functions cannot accidentally modify it), but its life spans the "entire Program". To achieve this, the compiler pulls it off the Stack entirely and permanently allocates it in the **BSS** segment (since its default value is `0`) or the **DS** segment (if you initialize it). It survives function returns.

- **`extern` (DS / BSS across modules):** The table shows `extern` has a scope and life of "entire Program" and defaults to `0`. This keyword does not allocate new memory; it tells the linker to look at the **DS/BSS** segment of a completely different `.c` file to find the shared hardware variable.

- **`register` (CPU Core Registers):** Like `auto`, its scope and life are restricted to the function body, and it defaults to a Garbage Value. However, this keyword begs the compiler to bypass RAM (Stack) completely and store the variable directly inside the CPU's internal hardware registers (e.g., `R0`-`R12` on an STM32 ARM Cortex-M). This is used in highly time-critical Interrupt Service Routines (ISRs) to shave off nanoseconds of memory access latency.

## auto storage class

- Because `auto` is the default storage class for variables declared inside a block,
  explicitly writing the keyword is entirely optional.
- In older C standards, if a type is omitted, the compiler implicitly assumes an `int`.
- The compiler treats every one of these as identical.
  - `auto int a`;
  - `int auto a`;
  - `auto a`;

### Block Scope and Auto Variable Life

```c
#include <stdio.h>

int main() {
    // ==========================================
    // 1. Outer Block Variable ('a')
    // ==========================================
    int a;                                      // starts with GV
    a = 10;                                     // Initialized, replacing Garbage Value (GV)

    // ==========================================
    // 2. Inner Block Scope ('b')
    // ==========================================
    {
        int b;
        b = 20;                                 // Initialized, replacing GV
        printf("%d", b);
    }                                           // Inner block ends here

    // ==========================================
    // 3. Post-Block Execution and Scope Error
    // ==========================================
    printf("%d", a);

    /*
       EXPLANATION OF COMPILER ERROR:
       The board labels the following line as (1).
       If (1) is present, the compiler throws "c.E: undefined symbol 'b'".
       If (1) is NOT there, the program outputs: "20 10".

       This happens because the 'auto' storage class restricts a variable's life
       strictly to the body `{}` in which it was declared. Once the inner body
       closes, 'b' ceases to exist in memory.
    */
    printf("%d", b);                         // (1) -> c.E: undefined symbol 'b'

    return 0;
}

/*
   FLOW DIAGRAM (Memory Scope):
   Visualize this block scope destruction with an 'X'.

   main()
   +-----------------------------------------+
   |   a                                     |
   |  +--------+                             |
   |  | ~~GV~~ | 10                          |
   |  +--------+                             |
   |                                         |
   |   +---------------------------------+   |
   |   | b                               |   |
   |   | +--------+                      |   |
   |   | | ~~GV~~ | 20                   |   |
   |   | +--------+                      |   |
   |   +---------------------------------+   |
   |                   X                     | (Inner block is destroyed)
   +-----------------------------------------+
*/

```

When building hardware abstraction layers for the project, this specific `{}`
block-scoping behavior is a powerful tool for optimizing Stack memory on STM32
and TI C2000 microcontrollers.

Because `auto` variables are strictly bound to their enclosing brackets, the CPU dynamically
manipulates the Stack pointer. When execution enters the inner block, it pushes `b` onto the
Stack. When it hits the closing `}`, it immediately pops `b` off, freeing those bytes of RAM.
This allows you to declare temporary variables for heavy, localized math calculations inside a
large function, knowing that the memory will be immediately reclaimed for other uses long
before the parent function actually finishes executing.

### Variable Shadowing and Scope Resolution

- We can define N variable with same name in different scope

```c
#include <stdio.h>

// ==========================================
// 1. Global Scope
// ==========================================
/*
   global variable 'a' initialized to 10 outside of main().
*/
int a = 10;

int main() {
    // ==========================================
    // 2. Outer Block Scope (Shadows Global)
    // ==========================================
    /*
       A new local variable 'a' is declared. This "shadows" the global 'a'.
       The compiler will prioritize this local 'a' over the global one for any
       references inside this block.
    */
    int a;
    a = 20;                                     // Replaces Garbage Value (GV)

    // ==========================================
    // 3. Inner Block Scope (Shadows Outer)
    // ==========================================
    {
        /*
           Yet another local 'a' is declared inside this inner block.
           This shadows the 'a' (20) from the outer block.
        */
        int a;
        a = 30;                                 // Replaces Garbage Value (GV)

        // Prints the innermost 'a' (30)
        printf("%d", a);
    }                                           // Inner block is destroyed

    // ==========================================
    // 4. Post-Block Execution
    // ==========================================
    /*
       The inner 'a' (30) is destroyed. The scope falls back to the outer 'a' (20).
    */
    printf("%d", a);                            // Prints 20

    // Final Output shown on board: 30 20
    return 0;
}
```

While the C compiler perfectly handles variable shadowing, it is universally banned in strict
embedded environments. MISRA C guidelines explicitly forbid declaring a local variable with
the same name as a variable in an outer scope or global scope.

When building complex hardware abstraction layers, variable shadowing is a primary cause of
silent, catastrophic bugs. If you have a global variable tracking a critical BMS state (like
`voltage_mV`), and you accidentally declare a local `int voltage_mV` inside a filtering loop,
the compiler will quietly update the temporary Stack variable instead of the permanent global
state. When the loop ends, the Stack variable is destroyed, the global state remains
unchanged, and the hardware behaves unpredictably without throwing a single compile error.

Strict naming conventions (like prefixing globals with `g_`) are mandatory for
deterministic firmware.

### Loop Block Scope and Variable Shadowing

```c
#include <stdio.h>

int main() {
    // ==========================================
    // 1. Outer Loop Control Variable
    // ==========================================
    int a;
    a = 1;

    // ==========================================
    // 2. Loop Condition and Post-Increment
    // ==========================================
    /*
       The while loop condition 'a++ <= 3' evaluates the condition first, then increments.
       - Iteration 1: Checks 1 <= 3 (True), outer 'a' becomes 2.
       - Iteration 2: Checks 2 <= 3 (True), outer 'a' becomes 3.
       - Iteration 3: Checks 3 <= 3 (True), outer 'a' becomes 4.
       - Iteration 4: Checks 4 <= 3 (False), outer 'a' becomes 5, and the loop terminates.
    */
    while(a++ <= 3)
    {
        // ==========================================
        // 3. Inner Block Scope Creation & Destruction
        // ==========================================
        /*
           A new local variable 'a' is declared, shadowing the outer loop counter.
           It is initialized to 100, printed, and then incremented to 101.
           When the closing brace is reached, this inner 'a' is destroyed.
           these are "automatically created & destroyed" each cycle.
        */
        int a = 100;
        printf("%d ", a);
        ++a;
    }

    // ==========================================
    // 4. Post-Loop Execution
    // ==========================================
    /*
       The outer 'a' has survived the loop and holds the final post-incremented value of 5.
    */
    printf("%d", a);

    // Final Output: 100 100 100 5
    return 0;
}

/*
   FLOW DIAGRAM (Iterative Stack Memory Allocation):

   main()
   +-----------------------------------------------+
   |   a                                           |
   |  +----+                                       |
   |  | ~~GV~~ | ~~1~~, 2, 3, 4, 5                 |
   |  +----+                                       |
   |                                               |
   |  -> Iteration 1 Block                         |
   |   +---------------------------------------+   |
   |   |   a                                   |   |
   |   |  +-----+                              |   |
   |   |  | ~~100~~ | 101                      |   |
   |   |  +-----+                              |   |
   |   +---------------------------------------+   |
   |                      X                        |
   |                                               |
   |  -> Iteration 2 Block                         |
   |   +---------------------------------------+   |
   |   |   a                                   |   |
   |   |  +-----+                              |   |
   |   |  | ~~100~~ | 101                      |   |
   |   |  +-----+                              |   |
   |   +---------------------------------------+   |
   |                      X                        |
   |                                               |
   |  -> Iteration 3 Block                         |
   |   +---------------------------------------+   |
   |   |   a                                   |   |
   |   |  +-----+                              |   |
   |   |  | ~~100~~ | 101                      |   |
   |   |  +-----+                              |   |
   |   +---------------------------------------+   |
   |                      X                        |
   |                                               |
   | "automatically created & destroyed"           |
   +-----------------------------------------------+
*/

```

For embedded development on the project, declaring `auto` variables inside high-frequency
polling loops (like RTOS task loops or sensor read loops) requires careful consideration.
While the C standard dictates that these local variables are "automatically created &
destroyed" on the Stack during every single iteration, modern cross-compilers (like GCC for
STM32 or TI Arm Clang for C2000) will heavily optimize this. Instead of physically pushing and
popping the Stack Pointer thousands of times per second—which would waste precious CPU clock
cycles—the compiler will typically allocate a permanent memory offset in the Stack frame or
dedicate an internal CPU hardware register to hold that inner variable for the lifetime of the
loop.

However, variable shadowing within a loop (where the inner variable shares the exact same name
as the loop control variable) is a critical MISRA C violation. It creates a severe risk of
infinite loops or memory corruption if an engineer attempts to modify the loop counter but
accidentally alters the shadowed inner variable instead.

### Bypassing Initialization with Goto vs. Standard Control Flow

```c
#include <stdio.h>

void execute_goto_trap() {
    // ==========================================
    // 1. The Goto Scope Trap
    // ==========================================
    int a = 10; // Outer 'a' initialized to 10 during execution not at compile time

    /*
       The board draws an arrow from 'goto inside;' directly jumping over the
       inner block's variable initialization.
    */
    goto inside;

    {
        /*
           Because of block scoping rules, the compiler allocates space for this
           inner 'a'. However, because the 'goto' command jumped completely over
           this line of code, the assignment '= 20' never actually executes.
        */
        int a = 20;
        {
            inside:
            /*
               This printf refers to the inner 'a' (due to shadowing).
               Since the inner 'a' was allocated but never initialized, it holds
               whatever residual memory was left in the Stack.
               The board explicitly labels the output as "Garbage Value".
            */
            printf("%d", a);
        }
    }
}

void execute_standard_flow() {
    // ==========================================
    // 2. Standard Block Reassignment - False
    // ==========================================
    int a_top = 10;

    if(2 > 3)                                   // Evaluates to False
    {
        // The board marks this assignment with an 'X' indicating it is skipped.
        a_top = 20;
    }

    printf("%d\n", a_top);                      // Output: 10

    // ==========================================
    // 3. Standard Block Reassignment - True
    // ==========================================
    int a_bot = 10;

    if(3 > 2)                                   // Evaluates to True
    {
        // Modifies the outer variable (no 'int' keyword here, so no shadowing)
        a_bot = 20;
    }

    printf("%d", a_bot);                        // Output: 20
}
```

In embedded systems development, above example demonstrates precisely why the `goto`
statement is universally banned by strict standards like MISRA C.

When you use standard control structures like `if`, `while`, or `switch` the compiler
guarantees that variable scope and initialization are handled predictably. However, using
`goto` to forcefully manipulate the program counter allows the CPU to enter a memory scope
without executing the corresponding initialization instructions.

## static storage class

```c
// Auto vs. Static Variable Life and Scope

#include <stdio.h>

// ==========================================
// 1. Function with Auto and Static Variables
// ==========================================
void test() {
    /*
       'l' is an 'auto' variable. It is created and destroyed on the Stack
       every single time test() is called. It is initialized to 0 each time.
    */
    auto int l = 0;

    /*
       's' is a 'static' variable. Its initialization (s = 0) happens ONLY ONCE
       at the start of the entire program.
       It is placed outside the Stack, so it survives function exits.
    */
    static int s = 0;

    ++l;                                        // Increments the temporary Stack variable
    ++s;                                        // Increments the persistent static variable

    printf("%d %d\n", l, s);
}

// ==========================================
// 2. Execution Flow and Scope Checking
// ==========================================
int main() {
    // Call 1: 'l' is created (0->1). 's' initializes (0->1).
    test();                                     // Outputs: 1 1

    // Call 2: 'l' is recreated (0->1). 's' persists and increments (1->2).
    test();                                     // Outputs: 1 2

    /*
       SCOPE TRAP:
       "C.E: undefined Symbol".
       Even though 's' is alive in memory for the "entire Program", its scope
       (visibility) is strictly confined to the body of test(). main() cannot see it.
    */
    printf("%d", s);

    // Call 3: 'l' is recreated (0->1). 's' persists and increments (2->3).
    test();                                     // Outputs: 1 3

    return 0;
}

/*
   FLOW DIAGRAM (Memory Architecture):

          main()                                    [Persistent Memory]
   +-------------------+                                  s
   |         X         |----------+                     +---+
   +-------------------+          |                     | 0 | (Init once)
      |      |      |             |                     | 1 | (Call 1)
      |      |      |             |                     | 2 | (Call 2)
      |      |      +-- Call 3    |                     | 3 | (Call 3)
      |      +--------- Call 2    |                     +---+
      +---------------- Call 1    |
                                  v
   +-------------------+    +-------------------+    +-------------------+
   | test()     [Call 1|    | test()     [Call 2|    | test()     [Call 3|
   |   l               |    |   l               |    |   l               |
   | +---+             |    | +---+             |    | +---+             |
   | | 0 | 1           |    | | 0 | 1           |    | | 0 | 1           |
   | +---+             |    | +---+             |    | +---+             |
   |         X         |    |         X         |    |         X         |
   +-------------------+    +-------------------+    +-------------------+
    (Destroyed)              (Destroyed)              (Destroyed)
*/

```

This is one of the most critical concepts for embedded systems development. By using the
`static` keyword, the compiler completely removes `s` from the CPU's Stack segment. Because it
is initialized to `0`, it is permanently placed in the microcontroller's **BSS** memory
segment (or the **Data** segment if initialized to a non-zero value).

## extern storage class

### Global Variable Scope and Default Initialization

```c

#include <stdio.h>

// ==========================================
// 1. Global Variable Declaration
// ==========================================
/*
   'g' is declared globally, outside of any function body.
   Because it is a global variable with an 'entire Program' scope, the compiler
   automatically initializes it to 0 and makes it visible to all functions.
*/
int g;

// ==========================================
// 2. Global Modification by Sub-Function
// ==========================================
void abc() {
    ++g;                                        // Increments the persistent global 'g'
}

// ==========================================
// 3. Execution Flow
// ==========================================
int main() {
    // main() increments the global 'g' (0 -> 1)
    ++g;

    // abc() is called and increments the exact same global 'g' (1 -> 2)
    abc();

    printf("%d", g);

    // Final output shown at the bottom of the board: 2
    return 0;
}

/*
   FLOW DIAGRAM (Global Memory Architecture):
   The global variable lives in a persistent memory segment completely separate
   from the Stack frames of main() and abc().

         [Persistent Memory]
               g
             +---+
             | 0 | (Implicit Initialization)
             | 1 | (Incremented by main)
             | 2 | (Incremented by abc)
             +---+
               ^
               | (Shared Access)
        +------+------+
        |             |
   +---------+   +---------+
   | main()  |   | abc()   |
   | Frame   |   | Frame   |
   +---------+   +---------+
     (Stack)       (Stack)
*/

```

This whiteboard locks in the final piece of the memory layout puzzle. Because `int g;`
is declared globally and remains uninitialized by the programmer, the C compiler assigns
it to the **BSS (Block Started by Symbol)** segment of memory. When your microcontroller
boots up, the C startup code (usually an assembly file like `startup_stm32.s`)
physically clears the entire BSS segment of RAM to zeros before `main()` is ever
called. If you had written `int g = 5;`, the compiler would have placed it in
the **DS (Data Segment)** instead.

Global variables like this are highly discouraged for system stability.
Because `g` is globally exposed to every function, it creates a severe vulnerability
to race conditions. If an Interrupt Service Routine (ISR) fires while `main()` is
in the middle of reading `g`, the ISR could modify the value, corrupting the main
loop's logic. This is precisely why strict standards like MISRA C prefer the
`static` variables to hide and protect hardware state within specific driver
modules, keeping it safely isolated from the rest of the program.

### Forward Declaration and the 'extern' Keyword

```c
#include <stdio.h>

// ==========================================
// 1. The Bug: Top-to-Bottom Visibility Failure
// ==========================================

void test_buggy() {
    // The compiler reads top-to-bottom. At this exact line, it has never
    // seen the variable 'g'. so C.E: undefined Symbol g"
    ++g;
}


// ==========================================
// 2. The Solution: 'extern' Declaration
// ==========================================
void test_fixed() {
    /*
       By adding 'extern int g;', we provide a forward declaration.
       This tells the compiler: "I promise a global integer named 'g' exists
       somewhere else in memory. Do not allocate new Stack space for it, just
       trust me and let this compile."
    */
    extern int g;                               // variable declaration
    ++g;                                        // Compilation succeeds
}

// ==========================================
// 3. The Definition
// ==========================================
/*
   This line is variable definition.
   This is where the compiler actually allocates physical BSS memory for 'g'.
*/
int g;

void abc() {
    ++g;
}

int main() {
    ++g;                                        // main increments g (0 -> 1)
    abc();                                      // abc increments g (1 -> 2)

    // In the fixed version, test() would increment it to 3, though the board
    // retains the previous output of '2' for continuity of the diagram.
    test_fixed();

    printf("%d", g);
    return 0;
}
```

In embedded systems architecture, this demonstrates the exact mechanism used to
share state across multiple `.c` files, though it is applied locally here to
solve a top-to-bottom compilation issue.

When you define a global hardware configuration struct (e.g., `SPI_Config_t global_spi_cfg;`)
in `spi_driver.c`, that physical memory is allocated exactly once. If you need to access
that same configuration from `main.c`, you cannot redefine it, or the linker will
throw a multiple-definition error. Instead, you place the
`extern SPI_Config_t global_spi_cfg;` declaration into a shared `spi_driver.h` header file.

When `main.c` includes that header, the compiler uses the `extern` keyword to
successfully compile the code, leaving a blank address placeholder.
The linker then steps in during the final build stage, connects the `extern`

The compiler performs the Syntax and Semantic analyses on each file independently,
resulting in isolated `.o` (object) files.

It is solely the Linker's job to stitch those object files together, matching `extern`
declarations with their physical memory definitions to produce the final `.elf`
executable code that gets flashed to the MCU.

The platform-specific linker errors on the whiteboard are a daily reality in cross-platform development. If you miss a function definition while compiling with the GCC toolchain on Ubuntu Linux, you will see the exact `Undefined reference` error written on the board. If you compile that same project using the Texas Instruments compiler in Code Composer Studio (which heavily utilizes Windows-style symbol tracking), you will see the `Undefined Symbol` format with the prepended underscore.

In embedded C, you cannot simply write `0x40021000 = 0x01;` to turn on a peripheral,
because `0x40021000` is just a literal number—it lacks an L-value (a valid memory address container).
You must satisfy the Semantic Analyzer by explicitly casting that number to a pointer
`*(volatile uint32_t*)0x40021000 = 0x01;` to prove it points to a physical hardware address.

The rule "extern variable Cannot be initialized" is the exact reason why you
never assign values to variables inside a `.h` file. If you create a `clock_config.h`
file and write `extern uint32_t system_clock_hz = 16000000;`, it forces a hard definition.
If multiple `.c` files include that header, the compiler will attempt to define
that exact same variable in memory multiple times, causing massive linker collisions.

The correct embedded architecture standard is to put the strict declaration
(`extern uint32_t system_clock_hz;`) inside the header file, and put the actual
initialization (`uint32_t system_clock_hz = 16000000;`) inside exactly one `.c` source file.

The restriction on global `auto` variables also physically ties back to
microcontroller architecture. An `auto` variable belongs on the Stack. The Stack
is manipulated by the CPU dynamically pushing and popping frames during function calls.
Therefore, asking the CPU to put a global variable on the Stack before `main()` has
even been called (or a Stack frame has been created) is a physical impossibility
for the hardware.

```c
/*
   FLOW DIAGRAM (The Build Pipeline)
   Complete transformation from source text to machine binary.

         a.c
     +---------+          Compiler            +-------------+
     | C Code  | ---------------------------> | Object Code |
     +---------+                              +-------------+
                                                     |
                                                W: a.obj
                                                L: a.o
                                                     |
                                              Linker |
                                                     v
                                              +-------------+
                                              | 10110       |
                                              | 1110        |
                                              | 1111        |
                                              | 10100       |
                                              +-------------+
                                              Executable Code
                                                     |
                                                  Program
                                              Windows: a.exe
                                              Linux:   a.out
                                                       a.elf
                                                     |
                                                     +-----> Run -> o/p

   PIPELINE EXPLANATION:
   1. Compiler Phase: The compiler translates the human-readable C code ('a.c')
      into intermediate machine-level instructions called Object Code.
      The platform-specific extensions: Windows uses '.obj',
      while Linux uses '.o'.

   2. Linker Phase: The linker takes the generated object code and resolves all
      external dependencies (like the 'extern' variables from the previous boards),
      generating the final Executable Code, represented on the board by binary
      1s and 0s.

   3. Output Formats: The format of the final program depends entirely on the target
      operating system. Windows produces '.exe' files, whereas Linux produces
      '.out' or '.elf' files. Executing this final file generates the program
      output (Run -> o/p).

    Set of instructions is called not a program
    Set of executable instructions is called a program
*/

```

The linker then combines those `.o` files into the `.elf` (Executable and Linkable Format)
file mentioned at the bottom of the board. In embedded systems, the `.elf` file is the most
critical artifact of the build process. It contains not just the raw machine binary, but also
the strict memory map (where the Stack, BSS, and Data segments live) and the debug symbols.
When you connect a hardware debugger to step through your firmware, the
debugger reads the `.elf` file to map the raw CPU Program Counter back to your original C
source lines.

The only step this whiteboard omits—because it focuses on PC operating systems—is the final
embedded flash extraction. A bare-metal microcontroller cannot directly run an `.elf` or
`out` file because it lacks an OS loader to parse the file headers. To actually program the
hardware, you must use a utility like `objcopy` to strip the `.elf` headers away, leaving
behind a raw `.bin` or `.hex` file that is physically flashed into the microcontroller's
non-volatile ROM.

In embedded firmware development, Scenario 2 (the Linker Error) is one of the most common
pitfalls when structuring a new architecture. If you are compiling your project using the GCC
toolchain on Ubuntu for STM32, or using the TI Arm Clang compiler for your target, this exact
mistake results in a `multiple definition of 'g'` fatal linker error.

To prevent this, embedded engineers never manually write `extern int g;` directly into their
`c` files as shown on the whiteboard. Instead, we use header files to enforce Scenario 3
automatically:

1. You place `extern int g;` into `shared_data.h`.
2. Both `a.c` and `b.c` `#include "shared_data.h"`.
3. You provide the physical definition `int g = 10;` inside only one file (e.g., `a.c`).

This guarantees that every single `.c` module in your project compiles against the exact same
`extern` signature, and the linker smoothly resolves all references back to the single
physical memory allocation in the Data segment.

### File-Scope 'static' for Encapsulation (Privacy)

```c
// ==========================================
// File: 1.c (The Private Module)
// ==========================================
/*
   The global static variable as a "Private variable"
   and the static function as a "Private fn".
   Applying the 'static' keyword at the global level restricts the linker's
   visibility of these symbols strictly to the boundaries of 1.c.
*/
static int s = 10;                              //  Private variable

static void f1() {                              // Private fn
    // Accessing 's' inside 1.c is perfectly valid
}

void main() {
    // f2() is implicitly extern and defined in 2.c, so calling it works
    f2();

    // Accessing 's' and f1() inside 1.c works
    f1();
}

// ==========================================
// File: 2.c (The External Consumer)
// ==========================================
void f2() {
    /*
       Because 's' and 'f1' were declared 'static' in 1.c, they are completely
       invisible to the linker when compiling 2.c.
    */
    // s X
    // f1(); X
}

// ==========================================
// Global Function Defaults
// ==========================================
/*
   In C, all functions are globally visible (extern) by
   default unless you specifically lock them down using the `static` keyword.
*/
```

In standard C, there is no `private` or `public` keyword like you would find in C++ or Java.
This whiteboard demonstrates how embedded engineers enforce strict data encapsulation and
object-oriented design patterns within a purely procedural language.

For your project, applying `static` at the file scope is arguably the most important MISRA C
rule for writing safe hardware drivers.

Imagine you are writing `i2c_driver.c`. You might need an internal state machine variable
(`static I2C_State_t current_state;`) and an internal helper function
(`static void I2C_ResetBus();`). By slapping `static` on them, you physically hide them from
the Linker's global symbol table. If a junior engineer working on `sensor_app.c` tries to
aggressively reset the I2C bus by directly calling `I2C_ResetBus()` or tries to overwrite
`current_state`, the Linker will immediately throw a compilation error, exactly as shown in
`2c` on the whiteboard.

This guarantees that the only way other developers can interact with your hardware driver is
through the controlled, public API functions (like `f2()` on the board) that you intentionally
expose in your `.h` files. It completely eliminates namespace collisions (meaning you can have
a `static int count;` in ten different `.c` files without the linker crashing) and protects
your critical hardware registers from accidental tampering.

### Memory Segments

- Process Layout / Memory layout of a Process / Process Image

```c
/*
   FLOW DIAGRAM

   +-----------------------+
   |        Stack          | -> auto variables, parameter variables,
   |          |            |    return values, fn calls
   |          v            |
   |                       |
   |          ^            |
   |          |            |
   |        Heap           | -> DMA (Dynamic Memory Allocation)
   +-----------------------+
   |     Data Segment      | -> extern initialized variables
   |   (initialized DS)    |    static (local, global) variables
   +-----------------------+
   | BSS -> Block Started  | -> extern uninitialized variables
   | By Symbol (uninit DS) |    static (local, global) variables
   +-----------------------+
   |    Code Segment /     | -> All executable instructions
   |     text Segment      |    are stored
   +-----------------------+
*/

#include <stdio.h>

// ==========================================
// Global Scope Mapping
// ==========================================
int a;                                          // -> BSS (Uninitialized global)
int b = 10;                                     // -> DS (Initialized global)
static int c;                                   // -> BSS (Uninitialized static)
static int d = 20;                              // -> DS (Initialized static)

// ==========================================
// Function Scope & Execution Mapping
// ==========================================
/*
   The board explicitly maps the function itself to CS (Code Segment), while
   its parameters (x, y) map to SS (Stack Segment).
*/
int avg(int x, int y) {                         // fn -> CS | x, y -> SS
    int sum;                                    // -> SS (auto variable)
    sum = x + y;                                // -> CS (executable instruction)
    return sum / 2;                             // -> CS + SS (instruction + return value)
}

void main() {                                   // -> CS
    /*
       Multiple variables on one line: 'e' is uninitialized (but still Stack),
       'f' is initialized to 30 on the Stack.
    */
    int e, f = 30;                              // -> SS

    static int g;                               // -> BSS (uninitialized local static)
    static int h = 40;                          // -> DS (initialized local static)

    e = avg(f, h);                              // -> CS + SS (instruction + fn call/return)
}

// ==========================================
// The Zero-Initialization Optimization
// ==========================================
/*
   Even though 'k' is explicitly initialized, it is initialized to 0.
   The compiler smartly assigns this to BSS to save Data Segment space.
*/
int k = 0;                                      // -> BSS

```

- **Code Segment / text Segment:** This is permanently burned into your MCU's non-volatile
  Flash memory. this is where "All executable instructions are stored".

- **Data Segment (DS):** This contains your initialized `extern` and `static` variables.
  Because these need specific starting values (like `10` or `20`), those values must be stored
  in Flash. However, because variables must be modifiable, the C startup code physically copies
  these values from Flash into RAM before `main()` executes.

- **BSS Segment:** This contains your uninitialized globals, uninitialized statics, and
  variables initialized explicitly to `0` (like `int k = 0;`). Because everything here defaults
  to zero, the compiler does not waste precious Flash memory storing a massive block of zeros.
  Instead, it reserves empty space in RAM, and the startup code simply wipes that RAM block
  clean before execution.

- **Heap:** Marked as DMA for Dynamic Memory Allocation (`malloc`/`free`). In strict MISRA C
  environments and safety-critical firmware, the Heap is often completely disabled to prevent
  memory fragmentation and hard faults.

- **Stack:** This stores your `auto` variables, parameters, and return values. Notice the
  arrows on the board showing the Stack growing downwards while the Heap grows upwards. If your
  firmware uses FreeRTOS, every single task you create is allocated its own private
  Stack memory block. If a task nests too many function calls or declares too many local arrays
  (`SS`), the Stack arrow collides with the Heap/BSS boundary, resulting in a catastrophic Stack
  Overflow.

### Why are we dividing data segments into two parts?

- The answer to the question is pure storage optimization. We divide the Data Segment into DS
  and BSS to drastically reduce the size of the final executable file.

```c
// The BSS Optimization (Executable Size vs. RAM Footprint)

/*
   "Assume int 4" (4 bytes per integer).
*/

// ==========================================
// 1. Initialized Data (DS)
// ==========================================
/*
   These variables have specific values. The compiler must physically store
   the numbers 1, 2, ..., 100 inside the executable file.
   100 variables * 4 bytes = 400 Bytes.
*/
int g1 = 1;
int g2 = 2;
// ...
int g100 = 100;

// ==========================================
// 2. Uninitialized Data (BSS)
// ==========================================
/*
   These variables lack specific initialization. They default to zero.
   100 variables * 4 bytes = 400 Bytes.
*/
int a1;
int a2;
// ...
int a100;


/*
   FLOW DIAGRAM (The "Why" Behind BSS)

   1. EXECUTABLE CODE (On Hard Disk / Secondary Memory)
      +-----------------------------------------+
      |  Program (Samp.exe)                     |
      |   +-------+   +---------------------+   |
      |   |  DS   |   |        BSS          |   |
      |   | 400 B |   |      ~~400 B~~      |   | <-- Crossed out!
      |   +-------+   +---------------------+   |
      +-----------------------------------------+
                                 |
                                 v
                            [ 4B - 8B ]
                (information about uninitialize variables)

            |
        [ Loader ]
            |
            v

   2. PROCESS (In RAM / Primary Memory)
      +-----------------------------------------+
      |               +-------+   +-------+     |
      |               |  DS   |   |  BSS  |     |
      |               |  400  |   |  400  |     |
      |               +-------+   +-------+     |
      +-----------------------------------------+
*/

```

For the initialized variables (`g1` to `g100`), the executable file _must_ physically contain
400 bytes of data to remember all those specific numbers (`1, 2... 100`).

However, for the uninitialized variables (`a1` to `a100`), we know they will all just default
to zero. If the compiler grouped them together with the DS, it would have to write 400 bytes
of zeros into the executable file. If you had an array of 10,000 uninitialized integers, that
would waste 40,000 bytes of disk space just to store zeros!

Instead, the compiler isolates them into the **BSS** segment. As shown by the crossed-out `400
B` box, the compiler strips those zeros out of the file entirely. It replaces them with a tiny
metadata header (just `4B - 8B`) that simply tells the operating system: _"Information about
uninitialize variables: Please allocate 400 bytes of empty space for me when you load this
program."_

When the `Loader` eventually moves the program from the Hard Disk (SM) into RAM (PM), it reads
that metadata, physically carves out the full 400 bytes in RAM for the BSS, and clears it to
zero.

**For Embedded project:**

This concept is absolutely critical for microcontrollers. On an STM32 or TI C2000, your
`Executable Code` lives in **Flash/ROM memory**, which is highly constrained (often just 128KB
to 512KB). Your `Process` memory is the **SRAM**.

By splitting the segments, your linker ensures that your `.elf`/`.bin` file only takes up
Flash memory for actual code and initialized DS data. The BSS segment takes up **zero bytes**
in your Flash memory. When the microcontroller powers on, a tiny assembly script in your
startup file (`Reset_Handler`) reads the BSS metadata and manually writes zeros across your
SRAM before it calls `main()`.

### Linker Segment Concatenation and Relocatable Object Files

```c
// ==========================================
// 1. Source Files
// ==========================================
/*
   File: 1.c
   int a = 10;

   File: 2.c
   int b = 20;
*/

/*
   FLOW DIAGRAM (Relocatable Object Resolution)

   The whiteboard visualizes how the linker resolves address collisions between
   independently compiled object files.

   PHASE 1: Independent Compilation (The Collision)
   Because the compiler processes files in isolation, it assigns a temporary
   base address (shown here as 100) to the Data Segment (DS) of both object files.

        1.c                               2.c
         |                                 |
         v                                 v
      1.obj                             2.obj
      (30B total)                       (30B total)
   +---------------+                 +---------------+
   | 100 a [10] DS | (10B)           | 100 b [20] DS | (10B)
   +---------------+                 +---------------+
   |      CS       | (20B)           |      CS       | (20B)
   +---------------+                 +---------------+
         |                                 |
         +----------------+----------------+
                          |
                          v Linker

   PHASE 2: Linker Concatenation (The Relocation)
   The linker breaks the object files apart, groups identical segments together
   (DS with DS, CS with CS), and recalculates the physical memory addresses to
   form a single contiguous block.

                  executable Code
   +-----------------------------------------------+
   | 10 Byte  a [10] -> 100 (Add)   | } 1.obj DS   |  <-- Base address retained
DS |--------------------------------|              |
   | 10 Byte  b [20] -> 110 (Add)   | } 2.obj DS   |  <-- Relocated! (100 + 10B)
   |================================|==============|
   |              20                | } 1.obj CS   |
CS |--------------------------------|              |
   |              20                | } 2.obj CS   |
   +-----------------------------------------------+
*/

```

When you compile independent C files, the compiler acts blindly. It creates `1.obj` and
`2.obj`, assigning `b` to the exact same temporary starting address (`100`) as `a`. If those
files were executed exactly as the compiler output them, `b` would overwrite `a` in memory.

The linker solves this through segment concatenation and address relocation. Instead of
stacking whole object files on top of each other, the linker rips them apart by segment type.
It takes the 10-byte Data Segment from `1.obj` and lays it down in RAM at address `100`. Then,
it grabs the 10-byte Data Segment from `2.obj`. Recognizing that address `100` is now
occupied, it _relocates_ `b`, physically shifting its address forward by 10 bytes to `110` so
it sits perfectly adjacent to `a` without colliding. It performs the exact same grouping
process for the 20-byte Code Segments (CS).

For your architecture, this visual perfectly explains the role of Linker Command files (`.cmd`
for the TI F28P65x or `.ld` for the STM32G474). When you compile massive hardware abstraction
layers, the GCC or TI compiler generates hundreds of isolated relocatable `.o` files that all
think they own address `0x00000000`.

The linker parses your `.cmd`/`.ld` script, groups every single `.data` (DS) section from your
I2C, SPI, and BMS driver object files, packs them consecutively into SRAM just like the
diagram shows, and groups all the `.text` (CS) instructions securely into non-volatile Flash.

## register storage class

- If a variable is used more frequently, especially in loops then we can use `register`
  storage class.
- Variable with register storage class whose size is more then CPU register size then
  that will be demoted to `auto` storage class.
- `register` is only applicable for local variables

```c
// The 'register' Storage Class and Hardware Overhead

#include <stdio.h>

void main() {
    // ==========================================
    // 1. The Bottleneck: Stack Memory Access
    // ==========================================
    /*
       The board shows a standard local variable 'int a;'.
       Because it is an 'auto' variable by default, it lives in the RAM STACK.
    */
    int a;

    /*
       The loop runs 10,000 times.
       For every single loop iteration (a = a + 1), the Processor
       must fetch the value from the STACK in RAM, load it into a CPU Register,
       have the ALU add 1, and then push it back across the bus into the RAM STACK.
    */
    for (a = 1; a <= 10000; a = a + 1) {
        // Some Job
    }
}

// ==========================================
// 2. The Solution: CPU Register Allocation
// ==========================================
/*
   To eliminate the RAM read/write overhead, the board points 'int a;' to an
   alternative declaration: 'register int a;'.
   This explicitly asks the compiler to permanently lock the variable inside the
   Processor's CPU Register, completely bypassing the RAM STACK for lightning-fast
   ALU access during the 10,000 loop iterations.
*/

// ==========================================
// 3. The Compiler Fallback (Hardware Constraints)
// ==========================================
void hardware_limit_example() {
    /*
       The board draws a dashed box around 'register' and points it to 'auto'
       for the declaration 'register double d;'.

       CPU registers are scarce hardware resources (typically 32-bit on an STM32).
       A 'double' requires 64 bits. If the microcontroller lacks a 64-bit hardware
       floating-point register, the compiler physically cannot honor the request.
       Instead of crashing, it silently downgrades the storage class back to 'auto'
       and places it on the STACK.
    */
    register double d;
}

/*
   FLOW DIAGRAM (RAM vs. Processor Overhead)

       RAM                          Processor
   +-------------------+          +-------------------+
   | Process           |          |  ALU              |
   |   +-------------+ |          | +---------------+ |
   |   | STACK       | |  Fetch   | |               | |
   |   |   a         | | -------> | +---------------+ |
   |   | +---+       | |          |  CPU Register     |
   |   | | 1 |       | |  Store   | +---------------+ |
   |   | +---+       | | <------- | |               | |
   |   +-------------+ |          | +---------------+ |
   +-------------------+          +-------------------+
*/

```

This example directly visualizes the physical gap between your microcontroller's SRAM and its
CPU core. Fetching data across the internal bus matrix from SRAM takes significantly more
clock cycles than accessing the CPU's internal R0-R15 registers.

When building low-level hardware abstraction layers, you might be tempted to use `register`
for highly critical loops, such as shifting bits out to an SPI peripheral or rapidly reading
ADC values.

However, in modern embedded C development, the `register` keyword is largely considered
deprecated. When you compile your code using GCC or the TI Arm Clang compiler with
optimization flags enabled (like `-O2` or `-O3`), the compiler's register allocator algorithm
is incredibly aggressive. It will automatically analyze variable lifespans and promote heavily
used `auto` variables into CPU registers without you ever writing the `register` keyword. In
fact, modern compilers will routinely ignore your `register` requests entirely if they
calculate a more efficient mathematical mapping for the available CPU registers.

Additionally, because a variable stored in a CPU register physically lacks a memory address in
RAM, you cannot use the address-of operator (`&a`) on a `register` variable. Attempting to
pass a pointer of a `register` variable to another function will instantly trigger a fatal
compilation error.

### Storage Classes in Function Parameters

- Explicitly allowed storage class in function parameter is `register`.
- A variable can have atmost 1 storage class.

```c

// ==========================================
// a) The 'auto' Modifier (Invalid)
// ==========================================
   void test(auto int i) { }
/*
   While function parameters inherently have automatic storage duration (they
   live and die on the Stack or in registers during the function call), the C
   standard explicitly prohibits writing the 'auto' keyword in a parameter list.
*/

// ==========================================
// b) The 'extern' Modifier (Invalid)
// ==========================================
   void test(extern int i) { }
/*
   'extern' tells the linker that a variable is physically defined globally
   elsewhere in the project. A parameter, however, is a localized input passed
   dynamically by the caller. It cannot simultaneously be a global memory address.
*/

// ==========================================
// c) The 'register' Modifier (Valid)
// ==========================================
   void test(register int i) {
       for(i=1; i<=10000; i=i+1)
   }
/*
   This is the ONLY legal storage class modifier for a function parameter in C.
   Because the parameter 'i' acts as a counter for a 10,000-iteration loop,
   requesting the compiler to lock it in a CPU register prevents the ALU from
   having to execute 10,000 read/write operations to the RAM Stack.
*/

// ==========================================
// d) The 'static' Modifier (Invalid)
// ==========================================
   void test(static int i) { }
/*
   A 'static' variable is initialized exactly once and permanently retains its
   value in the Data or BSS segment. A parameter's entire purpose is to accept
   a brand-new, dynamically generated value from the caller every single time
   the function executes (first 10, then 20). These two concepts are
   mechanically contradictory.
*/
```

## Summary

- Who is telling which variable to store which location?
  - storage class
  - This tells where memory allocated, when memory created and when memory destroyed
  - `static` and `extern` are destroyed when program completed
  - `auto` is destroyed when function completed
  - `register` is destroyed when function completed

- Who is telling scope of the variable?
  - storage class

- Who is telling how many bytes allocation for variable?
  - data type
