### Macros

- This is not a text replacement but a token replacement
- The replacement happens before the compilation

```c
#include <stdio.h>

// ==========================================
// 1. Pre-processor Macro Expansion
// ==========================================
/*
   The pre-processor replaces all instances of 'i' with '5' before the
   actual compilation begins. This happens entirely in text.
*/
#define i 5

int main() {
    /*
       Source code as written in IDE:
       printf("%d", i);

       Expanded Source Code passed to Compiler:
       printf("%d", 5);
    */
    printf("%d\n", i);

    return 0;
}

/*
===============================================================================
2. Build Process / compilation Process
===============================================================================

  .c (Source code)
         |
         v Pre-processor
         |
  Expanded Source Code
         |
         v Compiler
         |
  assembly code
         |
         v assembler
         |
  Object code
         |
         v Linker
         |
  executable code  -----> .Elf, .hex, .exe, .out, .bin, .cfg
         |
         v Loader
         |
  RAM -> debugger
*/
```

### Normal vs Argument Macros

```c

#include <stdio.h>

// ==========================================
// 1. Normal Macro
// ==========================================
#define i 5                                 // normal macro

void normal_macro_example() {
    // The pre-processor replaces 'i' with '5' before compilation.
    printf("%d", i);
}

// ==========================================
// 2. Argument Macro
// ==========================================
#define square(x) x * x                     // argument macro

void argument_macro_example() {
    int a;

    // Source code calls the macro with an argument of 4.
    a = square(4);
    printf("%d", a);

    /*
       | Pre-processor
       v
       Expanded code handed to the compiler:

       int a;
       a = 4 * 4;
       printf("%d", a);
    */
}

/*
===============================================================================
Macro Template vs Expansion (ASCII Visualization)
===============================================================================

      (   i       ) ---> macro Template
      ( square(x) )
            |
            | Maps downward during pre-processing phase
            v
      (   5       ) ---> macro Expansion
      (  x * x    )
*/

```

The pre-processor operates strictly through token substitution before the
compiler evaluates mathematical logic or types. Because `square(x)`
expands verbatim to `x * x`, passing expressions rather than single values
can yield unintended operator precedence issues (e.g., `square(2+2)` becomes
`2+2 * 2+2`, evaluating to 8 instead of 16).

### Advanced Macro Pitfalls and Edge Cases

```c
#include <stdio.h>

// ==========================================
// 1. Macros and L-Value Requirements
// ==========================================
#define A 100

void macro_lvalue_error() {
    /*
       A macro expands directly into literal text.
    */
    printf("%d", ++A); // expands to: printf("%d", ++100);

    /*
       You cannot increment a literal number, leading to a Compile Error.
       Output: CE. L-value req. (Compile Error: L-value required)
    */
}

// ==========================================
// 2. Masking Function Calls
// ==========================================
#define clrscr() 100

void masking_functions() {
    /*
       Macros can mimic and override function calls.
    */
    clrscr();
    printf("%d", clrscr());

    /*
       The pre-processor safely reduces the above to:
       100;
       printf("%d", 100);
    */
}


// ==========================================
// 3. Redefining Core Keywords
// ==========================================
/*
   WARNING: The following macro redefines a core C keyword.
*/
   #define int 100

   printf("int = %d", int);
/*
    Output: int = 100
*/

// ==========================================
// 4. Changing Data Types
// ==========================================
/*
   WARNING: Swapping data types causes hidden logic bugs.
*/
   #define int char

   int i;
   printf("%d", sizeof(i));

/*
   The 'int' keyword is replaced by 'char', causing sizeof to return 1
   instead of standard integer byte width.
*/

// ==========================================
// Macro Memory Allocation Fact
// ==========================================
#define i 5
// macro does not reserved memory


// ==========================================
// 5. Operator Precedence in Argument Macros
// ==========================================
#define mul(a, b) a * b

void precedence_issue() {
    int x;

    // The macro expansion blindly substitutes the text without calculating.
    x = mul(2 + 3, 3 + 2);

    // Output: 13
}

/*
===============================================================================
Argument Expansion Visualization
===============================================================================
                           (a) * (b)
                 Expected: (2+3) * (3+2) -> 25

    x = mul( 2+3 , 3+2 );
    |
    +-----> x = 2 + 3 * 3 + 2
            13
*/

// ==========================================
// 6. Ignoring Arguments
// ==========================================
#define f1(x) 100

void ignore_arguments() {
    printf("%d", f1(k));
    // Expands completely to 100, ignoring 'k'.
}

// ==========================================
// 7 & 8. Semicolon Traps
// ==========================================
#define a 5;

void semicolon_traps() {
    int i;

    // Case 7: Double Semicolons
    i = a;
    // Expands to: i = 5;; (Valid syntax, second ; is an empty statement)

    // Case 8: Syntax Corruption
    printf("%d", a);
    // Expands to: printf("%d", 5;);            // Compile Error

    i = a + a;
    // Expands to: i = 5; + 5;;                 // Compile Error
}
```

### Argument Macros: The Space Trap

```c
#include <stdio.h>

// ==========================================
// 1. Incorrect Macro Syntax
// ==========================================
/*
   A macro definition consists of four distinct parts:
   1) #                  2) define
   3) macrotemplate      4) macro Expansion

   If a space is placed between the macro name and its parameters,
   the pre-processor reads the parameters as part of the expansion.
*/

#define add (a, b) a+b

void space_trap_error() {
    int x;
    x = add(5,2);

    // Because of the space, the expansion replaces 'add' with everything
    // after it, treating '(a, b) a+b' as the raw text.

    // Expands to => x = (a, b) a+b(5,2);
    // This generates a Compile Error (C.E).
}

// ==========================================
// 2. Correct Macro Syntax
// ==========================================
/*
   Removing the space properly links the parameters (a, b) directly
   into the macrotemplate definition.
*/

#define add(a, b) a + b

int main() {
    int x;

    // The pre-processor safely maps 3 to 'a' and 2 to 'b'.
    x = add(3,2);

    // Expands to => x = 3 + 2;

    printf("%d\n", x);

    // Output: 5

    return 0;
}

/*
===============================================================================
Macro Template Breakdown
===============================================================================

   1      2         3                  4
  (#) (define) (  add  )      ( (a, b) a+b )      <-- Incorrect (Space)

  (#) (define) (add(a,b))     (   a + b    )      <-- Correct (No Space)
*/
```

### Multi-line Macros and Line Continuation

```c
#include <stdio.h>

// ==========================================
// 1. The Multi-line Macro Problem
// ==========================================
/*
   Without line continuation characters, the pre-processor terminates
   the macro definition at the end of the first physical line.
   The braces below it would be evaluated as detached global syntax.
*/
// #define infiniteloop while(1)                // Macro ends here
//                      {                       // Ignored by macro
//                         printf("hello");     // Ignored by macro
//                      }                       // Ignored by macro

// ==========================================
// 2. The Line Continuation Solution
// ==========================================
/*
   By appending a backslash (\) at the end of each line, we instruct
   the pre-processor to merge the physical lines into a single
   logical line during macro expansion.
*/
#define infiniteloop while(1) \
                     { \
                        printf("hello\n"); \
                     }

int main() {
    // Calling the multi-line macro
    infiniteloop

    return 0;
}
```

Using the backslash `\` operator is essential when writing complex hardware
macros in embedded systems, such as defining multi-step register unlock
sequences or bit-banging routines, as it keeps the source code readable
without breaking the pre-processor.

### Pre-processor Scope and Evaluation Rules

```c
#include <stdio.h>

// ==========================================
// Core Pre-processor Rules
// ==========================================
/*
   1) pre-processors can be written anywhere in the program
   2) Every Pre-processors will have Global Scope
   3) All pre-processors are evaluated from top to bottom.
*/

#define a 100                               // Top-level definition

void test();                                // Forward declaration

void scope_rules_example() {
    // The top-down parser applies the first macro it encountered.
    printf("%d ", a);                       // Expands to 100

    test();

    // Pre-processors can be placed anywhere, even inside functions.
    // This redefines 'a' for all subsequent code.
    #define a 10

    printf("%d ", a);                       // Expands to 10
}

void test() {
    // Because macros have Global Scope and are evaluated top to bottom,
    // this uses the redefined value (10), not the original (100).
    printf("%d\n", a);                      // Expands to 10
}

/*
===============================================================================
Execution Output
===============================================================================
   100 10 10
*/

```

### Syntax Modification and Macro Undefinition

```c
#include <stdio.h>

// ==========================================
// Un-defining Macros
// ==========================================

// Maps the identifier 's' to 's[]'
#define s s[]

void undefining_macros() {
    /*
       The pre-processor expands the left side of the assignment.
       Source code: char s = "hello";
       Expands to => char s[]="hello";
    */
    char s = "hello";                       // Valid array initialization

    /*
       If we try to print now, printf("%s", s); would expand to
       printf("%s", s[]); causing a compile error (C.E).

       We must destroy the macro to use the variable normally. Replacing it with
       itself (#define s s), which practically acts as an un-definition mapping
       to #undef s.
    */
    #undef s                                // => #undef s

    // Now 's' safely acts as the array pointer without expanding.
    printf("%s\n", s);                      // hello
}

```

### Why macro require?

- `#define A 10` this replace the token `A` with 10 but instead of using macro
  directly we can use 10. Why macro are used and what is real purpose?
- The answer is,
  - Macro are used for readability for constants usage
  - While using macro changing the macro will take effective in all the code
    but in harcoded program, programmer has to change

```c
#include <stdio.h>

// ==========================================
// 1. Global Definition Approaches
// ==========================================
/*
   To avoid hardcoding "magic numbers" throughout the code, we define
   them once globally. Updating the value here (e.g., 3.14 -> 3.142)
   automatically propagates the change throughout the program.
*/

// Approach A: Pre-processor Text Substitution
#define PI 3.14                             // -> 3.142

// Approach B: Read-Only Memory Variable
const float PI=3.14;                        // -> 3.142

void calculate_area_circumference() {
    int r;
    float c, a;

    // ------------------------------------------
    // Source Code Implementation
    // ------------------------------------------
    r = 5;
    c = 2 * PI * r;
    a = PI * r * r;

    r = 10;
    c = 2 * PI * r;
    a = PI * r * r;

    r = 20;
    c = 2 * PI * r;
    a = PI * r * r;
}

/*
===============================================================================
Expanded Code (What the Compiler Actually Sees)
===============================================================================

If `#define PI 3.14` is used, the pre-processor injects the literal float
value directly into the source text before compilation begins.

void main()
{
    int r;
    float c, a;

    r = 5;
    c = 2 * 3.14 * r;   // -> 3.142
    a = 3.14 * r * r;   // -> 3.142

    r = 10;
    c = 2 * 3.14 * r;   // -> 3.142
    a = 3.14 * r * r;   // -> 3.142

    r = 20;
}
*/
```

### Macro Expansion vs Constant Variables

- Macros perform raw text substitution: the literal `3.14` is copied to every
  line where `PI` is invoked.
- Conversely, using `const float` allocates a single read-only memory block, and
  all those lines would simply reference that single address.

### Limitations of `const` compared with macro

- Redeinition of constant is not possible in mid way but macros can do

```c
#include <stdio.h>

// ==========================================
// 1. Immutable Scope: const float
// ==========================================
/*
   A constant variable allocates a single read-only memory block.
   Its value propagates consistently downwards and cannot be altered
   or redefined midway through the file.
*/
const float PI_CONST = 3.14;

void f1_const() {
    // Accesses 3.14
}

void f2_const() {
    // Accesses 3.14
}

// const float PI_CONST = 360; -> This would trigger a Compile Error.

void f3_const() {
    // Accesses 3.14
}

// ==========================================
// 2. Mutable Pre-processor State: #define
// ==========================================
/*
   Macros are text substitutions evaluated top-to-bottom.
   They do not obey standard variable scope rules and can be silently
   redefined midway through a file, silently changing the behavior of
   functions defined below the redefinition.
*/
#define PI 3.14

void f1_macro() {
    // PI expands to 3.14
}

void f2_macro() {
    // PI expands to 3.14
}

// Redefining the macro midway through the file.
#define PI 360                                  //

void f3_macro() {
    // From this point downward, PI expands to 360 instead of 3.14.
    // This is a common source of bugs in large embedded projects.
}
```

If macros are used to resolve the limitation then why `const`?

### The real purpose of `const`

- `const` can be used in below situations

```c
#include <stdio.h>

// ==========================================
// 1. Constant Function Arguments
// ==========================================
/*
   By declaring function parameters as const, we guarantee that the
   function will not accidentally modify the passed values.
   This is critical for defensive programming.
*/
void add(const int x, const int y) {
    // x = x + 1; // Compile Error: assignment of read-only parameter
    printf("Sum: %d\n", x + y);
}

// ==========================================
// 2. Constant Structure Members
// ==========================================
/*
   making structure member as const
   This ensures specific fields (like a unique ID) remain immutable
   after initialization, even if the rest of the struct is mutable.
*/
struct emp {
    const int id;
    char name[36];
    int sal;
};

// ==========================================
// 3. Constant Structure Instances
// ==========================================
void struct_const_demo() {
    /*
       We can also apply const to the entire structure instance.
    */
    const struct emp e1 = {1, "abc", 3000};

    // Because e1 is const, all members are now locked in memory.
    // e1.sal = 5000; // Compile Error: assignment of read-only variable
}

// By placing `const` inside the structure definition, you enforce partial
// immutability. By placing `const` outside during instantiation,
// you enforce total immutability on that specific variable.
```

### Macro vs const

| Feature                 | Macro (#define)                                                                                                         | const Variable                                                                                                                          |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| How it works            | Textual substitution. The preprocessor physically replaces the macro name with its literal value before compilation.    | Read-only variable. It creates a true language-level variable that the compiler protects from being modified.                           |
| Type Safety             | No type checking. The compiler sees only raw literals, which can lead to unexpected type conversion errors.             | Strictly typed. The compiler verifies that data types match, preventing accidental type mismatch bugs.                                  |
| Scope                   | Global / File-level. It is accessible from the line it is defined until the end of the file (or until #undef).          | Block / Function-level. It respects traditional C scoping rules (e.g., inside {} braces).                                               |
| Memory Allocation       | Consumes no variable memory. Literal values are embedded directly into the instructions wherever used.                  | Consumes memory (unless optimized away by the compiler). It gets allocated in the stack or read-only data segment.                      |
| Debugging               | Harder to debug. The macro name disappears during preprocessing, meaning it won't show up in a debugger's symbol table. | Easy to debug. The variable exists in the symbol table, allowing you to inspect its value while debugging.                              |
| Pointers & Addresses    | Cannot take the address (&) of a macro.                                                                                 | You can take the address (&) of a const variable or point to it.                                                                        |
| C-Specific Capabilities | Can be used for global array sizes, switch case labels, and static variable initializations.                            | In standard C, it cannot be used for switch cases or static initialization because it is not considered a true "compile-time constant". |

## Macro vs Typedef

- #define vs typedef: Token vs Type Replacement

| Feature               | typedef                                           | Macro (#define)                                       |
| --------------------- | ------------------------------------------------- | ----------------------------------------------------- |
| Processed By          | Compiler (during compilation)                     | Preprocessor (before compilation)                     |
| Mechanism             | Creates actual type aliases                       | Performs blind text substitution                      |
| Scope                 | Follows local block and variable scope rules      | Global from the definition point onward               |
| Type Safety           | Enforced by the compiler                          | None (can cause hidden compilation errors)            |
| What it can represent | Only C data types (structs, pointers, primitives) | Anything (constants, expressions, code blocks, types) |
| Ending Semicolon      | Required (it is a C statement)                    | Not allowed (unless part of the substitution)         |

```c
#include <stdio.h>

// ==========================================
// 1. Non-Pointer Types: Identical Behavior
// ==========================================
#define ch_def char
typedef char ch_typ;

void non_pointer_comparison() {
    // Both define a standard char without issues.
    ch_def ch1;                                 // ch1 -> char
    ch_typ ch2;                                 // ch1 -> char
}

/*
===============================================================================
Non-Pointer Types Visualization
===============================================================================

  #define ch char                  |             typedef char ch;
                                   |
  . - - - - - - .                  |             . - - - - - - .
  | void main() |                  |             | void main() |
  | {           |                  |             | {           |
  |    ch ch1;  |                  |             |    ch ch1;  |
  | }           |                  |             | }           |
  ' - - - - - - '                  |             ' - - - - - - '
                                   |
     ch1 -> char                   |                ch1 -> char
*/

// ==========================================
// 2. The Pointer Trap
// ==========================================
#define ch_ptr_def char*                        // token Replacement
typedef char* ch_ptr_typ;                       // typeReplacement

void pointer_comparison() {
    /*
       Macro Token Replacement:
       The pre-processor performs blind text substitution.
       The code `ch_ptr_def p1, p2;` expands literally to `char * p1, p2;`
       This binds the pointer asterisk ONLY to p1.
    */
    ch_ptr_def p1, p2;
    // p1 -> char*
    // p2 -> char

    /*
       Typedef Type Replacement:
       The compiler treats ch_ptr_typ as a unified fundamental type.
       The pointer property is distributed to all variables on the line.
    */
    ch_ptr_typ p3, p4;
    // p3 -> char*
    // p4 -> char*
}

/*
===============================================================================
Token vs Type Replacement
===============================================================================

  #define ch char*                 |  typedef char *ch;
  void main()                      |  void main()
  {                                |  {
     ch ch1, ch2;                  |      ch ch1, ch2;
                                   |     // ch1 -> char*
    // ch1 -> char*                |     // ch2 -> char*
    // ch2 -> char                 |  }
   }                               |  typeReplacement
  token Replacement                |
*/

// ==========================================
// 3. Advanced Typedef Pointer Mechanics
// ==========================================
typedef int* P;

void advanced_pointers() {
    int a, *b;
    P c, *d;

    /*
       Evaluated Types Breakdown:
       a -> int
       b => int*
       c => int*  (Because P is int*)
       d => int** (P provides int*, *d adds a second level)
    */
}
```

## Macro vs Function

| Feature          | Macro (#define)                                                         | Function                                                                |
| ---------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| Processing Stage | Preprocessed before compilation.                                        | Compiled into machine code and executed at runtime.                     |
| Mechanism        | Simple text replacement in the source code.                             | Control jumps to the function address using a call stack.               |
| Type Safety      | No type checking; accepts any arguments (can cause bugs).               | Strict type checking for arguments and return values.                   |
| Execution Speed  | Faster; zero runtime overhead from function calls.                      | Slower; incurs overhead from stack allocation and register adjustments. |
| Code Size        | Increases binary size if used often (code is duplicated everywhere).    | Keeps binary size smaller (code exists in exactly one place).           |
| Debugging        | Harder to debug; symbols disappear after preprocessing.                 | Easier to debug using breakpoints and stack traces.                     |
| Side Effects     | Prone to side effects (e.g., passing i++ may increment multiple times). | Safe; arguments are evaluated exactly once before passing.              |

```c
// Macro vs Function: Execution and Stack Overhead

#include <stdio.h>

// ==========================================
// 1. Macro Implementation
// ==========================================
/*
   Macros perform blind inline text substitution before compilation.
   While this avoids the performance cost of a function call, it introduces
   dangerous operator precedence issues if arguments are not properly parenthesized.
*/
#define square_macro(x) x*x

void macro_behavior() {
    int a;

    a = square_macro(4);                        // Expands to 4 * 4
    // Result: 16

    // The Precedence Trap:
    // square_macro(3+2) expands directly to 3+2*3+2
    // Because multiplication has higher precedence, it calculates 3 + 6 + 2.
    // Result: 11 (Incorrect)
}

// ==========================================
// 2. Function Implementation
// ==========================================
/*
   Functions evaluate their arguments entirely before passing the resulting
   value into the function scope. This guarantees mathematical correctness
   but introduces "stack over head" (context switching, pushing arguments to
   the stack, and jumping to a new memory address).
*/
int square_func(int x) {
    return x * x;
}

void function_behavior() {
    int a;

    a = square_func(4);
    // Result: 16

    // Safe Evaluation:
    // square_func(3+2) evaluates 3+2 = 5 first, then passes 5 into the function.
    // Result: 25 (Correct)
}

/*
===============================================================================
Macro vs Function Execution
===============================================================================

  #define square(x) x*x               |   int square(int x)
                                      |   {
  void main()                         |      return x*x;
  {                                   |   }
     int a;                           |
     a = square(4);  -> 4*4           |   void main()
     printf("%d", a);                 |   {
  }                                   |      int a;
                                      |      a = square(4);
  16                                  |      printf("%d", a);     stack over
                                      |   }                       head.
  square(3+2); 11                     |
  3+2*3+2                             |   16      square(3+2)
                                      |           25
*/

```

This side-by-side comparison highlights the architectural trade-off in C: macros offer raw speed by eliminating the "stack over head" of function calls, but they lack type safety and evaluation safety. Modern C development for hardware often mitigates the macro precedence issue by aggressively wrapping macro arguments in parentheses (e.g., `#define square(x) ((x)*(x))`).

## Nested Macro

- Definition: one macro template is part of another macro expansion.
- When a macro is invoked, the pre-processor will recursively expand
  any other macros it finds within the resulting text.

```c
// Nested Macros and Complex Precedence Traps

#include <stdio.h>

// ==========================================
// nested macros
// ==========================================

// Example 1: Basic Nesting
#define square(x) x * x
#define cube(x) square(x) * x

// Example 2: The Precedence Nightmare
#define f1(n) n * (n - 1)
#define f2(n) f1(n - 1) * n

int main() {
    // ------------------------------------------
    // 1. Safe Nested Expansion
    // ------------------------------------------
    int a;

    // Passing a single integer literal expands safely.
    a = cube(4);
    printf("Cube result: %d\n", a);             // Output: 64

    // ------------------------------------------
    // 2. Unsafe Nested Expansion
    // ------------------------------------------
    // Passing an expression (8-1) into un-parenthesized nested macros
    // completely breaks the mathematical logic due to operator precedence.
    printf("Nested trap result: %d\n", f2(8 - 1)); // Output: -34

    return 0;
}

/*
===============================================================================
Expansion 1: cube(4) Visualization
===============================================================================

  a = cube(4);
        |
        +-----> square(4) * 4
                     |
                  4 * 4 * 4
                  ---------
                    16 * 4
                  ---------
                      64


===============================================================================
Expansion 2: f2(8-1) Visualization
===============================================================================

   f2(8-1) passes the raw text "8-1" into the parameter 'n'.

   f1(8-1-1) * 8-1
   8-1-1 * (8-1-1-1) * 8-1
   8-1-1 * (5) * 8-1

   Operator Precedence (Multiplication evaluates first):
   8-1-5 * 8-1

   7-40-1
```

This effectively demonstrates why passing expressions (like `8-1`) into nested, un-parenthesized macros creates severe and hard-to-track bugs. The compiler does not evaluate `8-1` to `7` before passing it; it passes the literal string `8-1`, allowing `*` to take precedence over `-` during the final compilation step.

## Stringification

```c
// Stringizing Operator and String Literals

#include <stdio.h>

// ==========================================
// 1. Macros and String Literals
// ==========================================
/*
   The pre-processor replaces parameter tokens throughout the macro,
   but it strictly ignores anything inside double quotes (string literals).
   Even though the parameter is confusingly named 'int', it only replaces
   the 'int' token outside the format string.
*/
#define print(int) printf("int = %d\n", int)

// ==========================================
// 2. The Stringizing Operator
// ==========================================
/*
   The '#' operator (stringizing operator) placed before a macro parameter
   converts the passed argument directly into a string literal.
   It automatically encloses the argument in double quotes.
*/
#define f(x) #x                                 // -> "x"

int main() {
    // ---------------------
    //  String Ignore
    // ---------------------
    int a = 10, b = 5;

    // 'a' replaces the 'int' argument outside the quotes, but the
    // "int =" inside the quotes remains untouched by the pre-processor.
    print(a);
    // Expands to => printf("int = %d\n", a);

    print(b);
    // Expands to => printf("int = %d\n", b);

    /*
       Output:
       int = 10
       int = 5
    */

    // -------------------
    // Stringizing
    // -------------------
    // f(hello) converts the raw text 'hello' into the string "hello".
    char str[] = f(hello);                      // -> "hello"

    printf("%s\n", str);

    /*
       Output:
       hello
    */

    return 0;
}

/*
===============================================================================
Macro Expansion Visualizations
===============================================================================

String Literal Exclusion
-------------------------------------------------------------------------------
  #define print(int) printf("int = %d\n", int)
                             ^            ^
                          Ignored      Replaced

  print(a);
    |
    +-----> printf("int = %d\n", a);


Stringizing Transformation
-------------------------------------------------------------------------------
  #define f(x)   #x
                 |-> "x"

  char str[] = f(hello);
                 |-> "hello"

  #hello -> "hello"
*/
```

```c
#include <stdio.h>

// ==========================================
// 1. The Flawed Macro
// ==========================================
/*

   string literals, hardcoding "int =" into the output.

#define print_old(int) printf("int = %d\n", int)

// ==========================================

// ==========================================

#define print_new(int) printf(#int" = %d\n", int)

int main() {
    int a = 10, b = 5;

    // ------------------------------------------
    // Old Behavior
    // ------------------------------------------

    print_old(b);

       printf("int = %d\n", b);

       int = 10
       int = 5
    */

    // ------------------------------------------
    // New Behavior
    // ------------------------------------------
    print_new(a);
    print_new(b);

       a = 10
       b = 5
    */

    return 0;
}
```

- This specific behavior is a common stumbling block: if you actually wanted to stringize the _value_ of `a` (to get `"5"`), you would need to use a two-step macro technique to force the pre-processor to expand `a` before stringizing it.

### Two-Step Macro Expansion: The Stringizing Bypass Technique

```c
#include <stdio.h>

// ==========================================
// 1. The Two-Step Definition
// ==========================================
/*
   To force the pre-processor to evaluate a macro before stringizing it,
   we must use two separate macros.

   The C pre-processor rule is: if a macro parameter is used with '#' or '##',
   it is NOT expanded. If it is used normally, it IS expanded.
*/

// Step 1: The inner macro that actually applies the '#' operator.
#define STR(x) #x

// Step 2: The outer macro that acts as a proxy.
// Because 'x' is not attached to '#' here, the pre-processor expands it first.
#define XSTR(x) STR(x)

#define a 5

int main() {
    // ------------------------------------------
    // The Direct Trap
    // ------------------------------------------
    // Passes 'a' directly to the stringizing operator.
    printf("Direct STR(a): %s\n", STR(a));
    // Output: a

    // ------------------------------------------
    // The Bypass Technique
    // ------------------------------------------
    // Passes 'a' to XSTR. Since XSTR doesn't stringize, 'a' expands to 5.
    // Then, 5 is passed to STR, which stringizes it to "5".
    printf("Bypass XSTR(a): %s\n", XSTR(a));
    // Output: 5

    return 0;
}

/*
===============================================================================
Two-Step Expansion Flow (ASCII Visualization)
===============================================================================

Direct Stringizing:
  STR(a)
    |
    +-----> #a
             |
             +-----> "a"

Indirect Stringizing (The Bypass):
  XSTR(a)
    |
    | (Pre-processor sees no '#' in XSTR, so it evaluates 'a' first)
    v
  STR(5)
    |
    | (Now STR applies the '#' operator to the evaluated result)
    v
    #5
    |
    v
   "5"
*/
```

- This two-step `STR`/`XSTR` pattern is an extremely common idiom in professional C codebases, especially when you need to convert version number macros or mathematical constants into printable strings for logging.

## Token pasting / Token merging

```c
#include <stdio.h>

// ==========================================
// 1. The Token Pasting Operator (##)
// ==========================================
/*
   The ## operator takes two separate tokens and physically glues them
   together to form a single, newly recognized C token before compilation.
*/
#define f(x, y) x##y                            // -> xy

// ==========================================
// 2. Generating Literal Values
// ==========================================
// Appends a hexadecimal prefix to a passed numerical token.
#define k(m) 0X##m

// Conceptually used for system calls like chmod to force octal mode.
#define OCTAL(val) 0##val

int main() {
    // ------------------------------------------
    // The Comment Trap
    // ------------------------------------------
    /*
       Attempting to merge tokens using inline comments does not work:
       int a/*hello* /b = 10;
       printf("%d", ab);

       The C pre-processor replaces comments with a single space.
       This expands to `int a b = 10;`, triggering a syntax error.
    */

    // ------------------------------------------
    // Basic Merging
    // ------------------------------------------
    int ab = 10;

    // f(a,b) expands to a##b, which merges into the valid identifier 'ab'.
    printf("Merged variable: %d\n", f(a, b));   // Output: 10

    // ------------------------------------------
    // Hexadecimal Evaluation (Right Board)
    // ------------------------------------------
    // k(13) expands to 0X##13, gluing them into the literal 0X13.
    // Using %d forces printf to evaluate and display it as a decimal integer.
    printf("Hex literal: %d\n", k(13));         // Output: 19

    return 0;
}

/*
===============================================================================
Token Merging Visualizations
===============================================================================

1. Hexadecimal Evaluation:
  k(13)
    |
    +-----> 0X ## 13
              |
              v
             0X13
              |
              v (Evaluated by compiler as base-16)
           3 * 16^0 =  3
         + 1 * 16^1 = 16
         ----------------
                      19

2. Octal Mode Merging for chmod():
  Instead of passing 777 directly (which the compiler reads as decimal),
  we paste a '0' to the front to construct an Octal literal token.

  [  0  ] ## [ 777 ]
     \          /
      v        v
      (  0777  )
*/

```

- The `##` operator is extensively utilized in embedded systems for macro-driven hardware abstraction, allowing you to dynamically construct register names (e.g., merging `PORT` and `A` to target `PORTA`) based on macro parameters.

### Advanced Token Pasting and Nested Macro Bypass

```c
#include <stdio.h>

// ==========================================
// 1. Pasting with Expressions
// ==========================================
#define fun(a, b) a##b

// ==========================================
// 2. Nested Token Pasting Bypase
// ==========================================
/*
   Similar to the stringizing operator (#), if a macro parameter is
   attached directly to the token pasting operator (##), the pre-processor
   will NOT expand it first.
*/
#define cat(x, y) x##y

/*
   To force the pre-processor to evaluate nested macros before pasting them,
   a two-step bypass technique is required. The 'xcat' proxy does
   not contain the '##' operator, forcing its arguments to be fully evaluated
   before being passed down to 'cat'.
*/
#define xcat(x, y) cat(x, y)

int main() {
    // ------------------------------------------
    // Evaluating Expressions During Pasting
    // ------------------------------------------
    int val1 = 10, val2 = 20, val3 = 30;

    /*
       fun(val, 1+2) takes 'val' and '1+2'. It pastes 'val' and '1' together
       to create the variable identifier 'val1'. The remaining '+2'
       is left as an independent mathematical token.
       Resulting code: val1 + 2
       Calculation: 10 + 2 = 12
    */
    printf("fun result: %d\n", fun(val, 1+2));  // Output: 12

    // ------------------------------------------
    // Nested Pasting Trap & Solution
    // ------------------------------------------
    int abc = 100;

    /*
       DIRECT TRAP: cat(cat(a,b), c)
       Because 'cat' uses '##', it blindly pastes the literal text of the
       arguments. It attempts to paste "cat(a,b)" and "c" into "cat(a,b)c".
       This generates a syntax/Compile Error (C.E: ES).

       // printf("%d", cat(cat(a,b), c));       // Compile Error
    */

    /*
       BYPASS SOLUTION: xcat(xcat(a,b), c)
       The inner xcat(a,b) expands to cat(a,b), which resolves to 'ab'.
       The outer xcat(ab, c) expands to cat(ab, c), which resolves to 'abc'.
    */
    printf("xcat result: %d\n", xcat(xcat(a,b), c)); // Output: 100

    return 0;
}

/*
===============================================================================
Expression Pasting Visualization
===============================================================================

  fun(val, 1+2)
       |
       +--> val ## 1 + 2
               |
             val1 + 2
              10  + 2
                12

===============================================================================
Nested Macro Bypass Visualization
===============================================================================

  xcat( xcat(a,b), c )
          |
          +--> cat(a,b) -> ab

  xcat( ab, c )
       |
       +--> cat(ab, c)
               |
              abc
               |
              100
*/

```

- This perfectly illustrates how `##` interacts dynamically with expressions and nested calls, a pattern heavily utilized when designing generic C macros for hardware abstraction layers.

## Conditional compilation

- Based on a condition some part of code is compiled and some part of code is
  not compiled that is called conditional compilation

- Unlike standard `if/else` logic (which executes at runtime), conditional
  compilation directives (`#ifdef`, `#ifndef`, `#if`) are evaluated by the
  pre-processor before compilation. Code blocks that fail the condition
  are entirely stripped from the final executable.

### Platform dependent vs Platform independent code

```c
// ==========================================
// The Platform Dependency Problem
// ==========================================
/*
   C is inherently platform dependent (OS + Processor).
   When C Source code is compiled on a 16bit Arch, it generates
   executable code specifically tailored for a 16 bit HW target.

   If you attempt to run that 16-bit executable on 32 bit or 64 HW,
   it will fail (marked with an X in the diagram). This is why C is
   used for Hardware Specific code -> C progr, such as device drivers,
   compiles, OS.

   By contrast, Java -> PF independent. Java Source code compiles
   into a unified .class file (Byte code). This 1Byte code is then fed
   into a JVM (Java Virtual Machine) which translates it on the fly for
   16B H/w, 32B, or 64B targets.
*/

/*
===============================================================================
C vs Java Architecture Visualizations
===============================================================================

C: Platform Dependent (Compile-Time Targeting)
-------------------------------------------------------------------------------
      Source code
           | 16bit Arch
           v
    executable code
        16 bit
      /    |     \
     /     |      \
 [16 bit] [32 bit] [64 H/w]
   H/W
    ok      X        X


Java: Platform Independent (Run-Time Translation)
-------------------------------------------------------------------------------
       Source code
            |
            v  Byte code
       . class file
         1Byte .
       /    |    \

     v      v      v
```

- Because C compiles directly into hardware-specific machine code, you cannot write a single piece of low-level driver logic that works on every processor. Conditional compilation is the solution to this: it allows developers to write multiple architecture-specific implementations in the same `.c` file, and selectively compile only the block relevant to the target hardware.

Here is a direct comparison between platform-dependent and platform-independent code:

| Feature              | Platform-Dependent Code                                                                       | Platform-Independent Code                                                                      |
| -------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| Core Definition      | Code tied to a specific operating system (OS) or hardware architecture.                       | Code that can execute across multiple different operating systems and hardware configurations. |
| Execution Philosophy | "Write Once, Compile Anywhere" (WOCA).                                                        | "Write Once, Run Anywhere" (WORA).                                                             |
| Compilation Output   | Direct native machine code (binary format specific to the target CPU/OS, e.g., .exe or .dmg). | Intermediate code or bytecode (a neutral format, e.g., .class).                                |
| Execution Speed      | Faster, because it runs directly on the hardware without any mid-flight translation.          | Slightly slower, as the intermediate code must be interpreted or translated at runtime.        |
| Hardware Access      | Has direct, unmediated access to system hardware resources and OS-specific APIs.              | Accesses system resources safely through an intermediary abstract layer.                       |
| Runtime Dependency   | Requires no special software or virtual machines to run once compiled.                        | Requires a Virtual Machine (e.g., JVM) or an interpreter installed on the host machine.        |
| Recompilation        | Must be recompiled separately for every single platform you want to support.                  | The same compiled bytecode file runs on any system without modifications.                      |
| Common Examples      | C, C++, Assembly, Swift (for native iOS apps).                                                | Java, Python, C#, JavaScript.                                                                  |

### Conditional Compilation: #else, #if, and #elif Directives

```c

#include <stdio.h>

// ==========================================
// 1. The #else Directive
// ==========================================
/*
   The #else directive provides a fallback path if the preceding #ifdef
   (or #ifndef/#if) condition evaluates to false.
*/

#define KEY                                     // (1)

void execute_ifdef_else() {
    printf("A\n");

    #ifdef KEY
        printf("B\n");
        printf("C\n");
    #else
        printf("D\n");
        printf("E\n");
    #endif

    printf("F\n");
}

/*
   Execution Scenarios for #ifdef / #else:
   - if (1) is there (KEY is defined): Code compiles A, B, C, F.
   - if (1) is not there (KEY is undefined): Code compiles A, D, E, F.
*/

// ==========================================
// 2. Expression Evaluation with #if and #elif
// ==========================================
/*
   Unlike #ifdef which only checks if a macro exists, #if evaluates
   mathematical expressions.
   - 0 is evaluated as False.
   - Any non-zero value (like 10) is evaluated as True.
*/

void execute_if_elif() {
    printf("A\n");

    #if 0
        printf("B\n");
        printf("C\n");
    #elif 0
        printf("D\n");
        printf("E\n");
    #endif

    printf("F\n");
}

/*
   Execution Scenarios for #if / #elif combinations:

   Single #if checks:
   - #if 10 evaluates True -> Compiles A, B, C, F.
   - #if 0 evaluates False -> Compiles A, D, E, F (assuming #else exists).

   #elif chain scenarios:
   - #if 10  #elif 10 -> First condition is true. Compiles A, B, C, F.
   - #if 0   #elif 10 -> Second condition is true. Compiles A, D, E, F.
   - #if 0   #elif 0  -> Both conditions false. Compiles only A, F.
*/

/*
    Valid Pairs
    #if -> #elif -> #else -> #endif
    #ifdef       -> #else -> #endif
    #ifndef      -> #else -> #endif
*/
```


- This literal copy-paste behavior is exactly why combining this concept with
  the conditional compilation directives we just covered (`#ifndef`, `#define`, `#endif`) is mandatory in C.

- If you have an embedded project where `sensor.c`, `display.c`, and `main.c`
  all `#include "shared_types.h"`, the pre-processor will blindly copy-paste the
  contents of `shared_types.h` multiple times into the final build, causing the compiler to throw "redefinition" errors.

- To solve this, we wrap the contents of every header file in a Conditional Compilation Guard.

```c
// Standard C Header Guard Implementation

// 1. Check if this specific token has NOT been defined yet.
#ifndef SHARED_TYPES_H

// 2. If it hasn't, immediately define it.
#define SHARED_TYPES_H

// 3. Place all the file contents
typedef struct {
    int id;
    int value;
} SensorData;

// 4. Close the condition.
#endif
```

- If the pre-processor tries to copy-paste this file a second time,
  `#ifndef SHARED_TYPES_H` will evaluate to false (because it was defined during the first
  pass), and the pre-processor will delete everything down to the `#endif`, protecting the compiler from duplicates.

### File Inclusion Syntax and Directory Search Paths

```c
// ==========================================
// 1. Search Path Rules
// ==========================================
/*
   The pre-processor uses different search paths depending on the delimiters
   used around the header file name.

   Syntax 1: #include <filename.h>
   -> Searches ONLY the Include Directory (ID).

   Syntax 2: #include "filename.h"
   -> Searches the Source Directory (SD) first. If not found, it falls back
      to the Include Directory (ID) [SD + ID].
*/

// ==========================================
// 2. Directory Environments
// ==========================================
/*
   Source directory (SD):
   The folder where your current .c file resides.
   Example: SOURCE DIR (E:\test) containing user files like 'a.h' alongside
   potentially 10k other files.

   Include directory (ID):
   The standard system folder where the compiler stores predefined libraries.
   Examples: \usr\include (Unix/Linux standard) or D:\tc (Turbo C path).
   Contains files like: stdio.h, math.h, string.h, stdlib.h, process.h,
   types.h, and limits.h.
*/

// ==========================================
// 3. Execution Scenarios and Results
// ==========================================

// Scenario 1: Standard System Header
#include <stdio.h>
/*
   Result: Success.
   Reason: Directly searches the Iinclude Directory, finds the public header
   (predefined header file) immediately.
*/

// Scenario 2: System Header with Quotes
#include "stdio.h"
/*
   Result: Success.
   Reason: Searches the SD first. Since it's not there, it automatically
   falls back to the ID and finds it. (Valid, but slightly slower than <>).
*/

// Scenario 3: Local Project Header
#include "a.h"
/*
   Result: Success.
   Reason: Searches the SD and successfully locates the private header
   (user defined header file).
*/

// Scenario 4: Local Header with Angle Brackets
// #include <a.h>
/*
   Result: C.E: unable to open a.h (Compile Error).
   Reason: The pre-processor ONLY checks the system ID. Since 'a.h' is in
   the local SD, it cannot be found.
*/

int main() {
    return 0;
}
```

- This perfectly maps out how the compiler resolves file dependencies.
  When you use `< >`, you are strictly telling the compiler to look in its standard
  installation directories (like `/usr/include`). When you use `" "`, you are
  telling it to look locally in your project folder first before checking the
  system libraries.

### Relative Pathing and Subdirectory Inclusion

```c
// ==========================================
// Directory Structure Context
// ==========================================
/*
   Assume the current Source Directory (SD) is E:\test

   E:\
   ├── test           <-- Current SD
   │   ├── a.h
   │   └── 111
   │       ├── 1.h
   │       └── 222
   │           └── 2.h
   └── 3.h            <-- Parent Directory
*/

// ==========================================
// Inclusion Scenarios
// ==========================================

// 1. Immediate Source Directory
#include "a.h"
/*
   Result: Success.
   The pre-processor looks directly in SD (E:\test) and finds it.
*/

// 2. Missing Path Declaration
// #include "1.h"
/*
   Result: Fails.
   The pre-processor only checks the root of the SD. It does not automatically
   search through subdirectories like '111'.
*/

// 3. Single Subdirectory Traversal
#include "111/1.h"
/*
   Result: Success.
   Explicitly tells the pre-processor to step into the '111' folder.
*/

// 4. Nested Subdirectory Traversal
#include "111/222/2.h"
/*
   Result: Success.
   Chains directories together to reach deeply nested header files.
*/

// 5. Parent Directory Traversal
#include "..\3.h"
/*
   Result: Success.
   The '..' operator tells the pre-processor to step UP one level, exiting
   the 'test' directory into the 'E:\' root to find '3.h'.
*/

int main() {
    return 0;
}

```

- Using Windows-style drive letters (`E:\test`) and backslashes (`..\3.h`),
  when writing cross-platform frameworks in an Ubuntu environment, it is best
  practice to strictly use forward slashes (`/`) for all relative paths (e.g., `../3.h`).

- The C standard mandates that compilers correctly resolve forward slashes across all operating systems, preventing compilation errors when code is ported between
  Linux and Windows build environments.

### Creation of user defined header files

```c
// Preventing Double Inclusion with Header Guards

// ==========================================
// 1. The Double Inclusion Problem
// ==========================================
/*
   File: a.h (Without Guards)
   void f1();
   void f2();

   File: a.c
   #include "a.h"
   #include "a.h"

   If a source file (or a chain of other headers) includes the same file
   multiple times, the pre-processor blindly copy-pastes the contents.

   Expanded Source Code sent to compiler:
   void f1();
   void f2();
   void f1();
   void f2();
   Result: Compiler throws a redefinition error (crossed out on the board).
*/

// ==========================================
// 2. The Header Guard Solution
// ==========================================
/*
   File: a.h (With Guards)
*/
#ifndef __A__H
#define __A__H

void f1();
void f2();

#endif

/*
   File: a.c
   #include "a.h"
   #include "a.h"
*/

/*
===============================================================================
Pre-Processor Execution Flow
===============================================================================

Pass 1 (First #include "a.h"):
-------------------------------------------------------------------------------
  #ifndef __A__H      --> True (__A__H does not exist yet)
  #define __A__H      --> Creates the __A__H macro token
      void f1();      --> Kept
      void f2();      --> Kept
  #endif

Pass 2 (Second #include "a.h"):
-------------------------------------------------------------------------------
  #ifndef __A__H      --> False (We defined it in Pass 1)
  #define __A__H      --> Skipped
      void f1();      --> x (Skipped/Deleted)
      void f2();      --> x (Skipped/Deleted)
  #endif

Final Expanded Source Code sent to compiler:
-------------------------------------------------------------------------------
  void f1();
  void f2();
*/
```

```c
/*1. Header guard */

• Use it for: Tiny, frequently-called functions (like clamping a number,
  converting Celsius to Fahrenheit, or checking a bitmask).
```

## Miscellaneous

```c
// Predefined Global Macros and Error Reporting

#include <stdio.h>

// ==========================================
// 1. Compiler Error Reporting
// ==========================================
/*
     File: test.c
   1 void main()
   2 {
   3    printf("hello")
   4 }

   When a syntax error occurs (like the missing semicolon on line 3),
   the compiler relies on predefined macros to generate the exact
   diagnostic message:

   test.c : Error Line 3 expected ;
*/

// ==========================================
// 2. Predefined Global Macros
// ==========================================
/*
   The pre-processor automatically populates these macros during compilation,
   making them invaluable for writing custom logging and debugging systems.
*/
// Sample.c

int main() {

    // __LINE__ evaluates to the current line number of the source file as an integer.
    printf("Line: %d\n", __LINE__);             // Outputs '3' conceptually

    // __FILE__ evaluates to the name of the source file as a string.
    printf("File: %s\n", __FILE__);             // Outputs 'Sample.c'

    // __TIME__ evaluates to the compilation time string in HH:MM:SS format.
    printf("Time: %s\n", __TIME__);

    // __DATE__ evaluates to the compilation date string (noted conceptually as DD:MM:YYYY).
    printf("Date: %s\n", __DATE__);

    return 0;
}

```

- These macros are completely static once compiled. The `__TIME__` and `__DATE__`
  reflect the exact moment the executable was built, not the time it is currently
  running on the processor.

### The #line Directive and Diagnostic Resyncing

```c
#include <stdio.h>

// ==========================================
// 1. Manual Line Override
// ==========================================
/*
   The `#line` directive forces the compiler to reset its internal line counter
   to a specific integer for the immediately following line of code.
*/
void manual_line_override() {

#line 100
    // The original line number (4) replaced by 100.
    printf("Line: %d\n", __LINE__);             // Output: 100

    // Subsequent lines increment naturally from the new starting point.
    // Line 5 becomes 101, line 6 becomes 102.
    printf("Next: %d\n", __LINE__);             // Output: 101
}

/*
===============================================================================
Manual Override Visualization
===============================================================================

  1. void main()
  2. {
  3.    #line 100
  4. -> 100  printf("%d", __LINE__);
  5. -> 101
  6. -> 102  }
*/

// ==========================================
// 2. Pre-Processor Auto-Resync
// ==========================================
/*
   Why does the `#line` directive exist? It is primarily a tool used by the
   pre-processor itself to ensure that compiler error messages in your IDE
   (like VS Code or Code Composer Studio) match your original source code.

   Original File:
   1 #include <stdio.h>
   2 void main()
   3 {
   4    printf("hello");
   5 }

   As established, stdio.h dumps 314 lines of code into the file.
   Without intervention, the compiler would think `void main()` starts on
   line 315. If you missed a semicolon on line 4, the compiler would report
   a syntax error on line 317—making debugging practically impossible.

   To fix this, the pre-processor automatically injects a `#line 2` directive
   immediately after the 314 lines of included text, forcing the compiler's
   tracker back in sync with your raw source file.
*/

/*
===============================================================================
Expanded Source Code sent to Compiler
===============================================================================

   ( 314 lines of stdio.h replaced )

       #line 2

   315 -> 2.  void main()
   316 -> 3.  {
   317 -> 4.     printf("hello");
   318 -> 5.  }
*/
```
