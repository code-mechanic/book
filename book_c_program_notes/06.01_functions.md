# Functions

```text
Functions

  (Redundant Code)                  (Using Functions)

  stm1;                             stm1;
+-------+                           m1; <------------.
| stm2; |                           stm5;            |
| stm3; |                           m1; <------------+---.
| stm4; |                           stm6;            |   |
+-------+                           stm7;            |   |
  stm5;                             m1; <------------+---+--.
 -------                            stm8;            |   |  |
| stm2; |                                            |   |  |
| stm3; |                                            |   |  |
| stm4; |                                            v   v  v
 -------                                           +--------+
  stm6;                                            | m1     |
  stm7;                                            |  stm2; |
 -------                                           |  stm3; |
| stm2; |                                          |  stm4; |
| stm3; |                                          +--------+
| stm4; |
 -------
  stm8;

```

The above visualizes the fundamental architectural shift from procedural
redundancy to modular programming. By extracting the repeating `stm2`, `stm3`,
`stm4` block into a single function `m1`, the visual highlights four core benefits:

1. **Code reusage:** This is the primary driver. You write the logic once and
   invoke it via its CS (Code Segment) memory address whenever needed.

2. **Debugging:** If a hardware fault occurs within `stm3`, you isolate and fix
   it in exactly one location, rather than hunting down every duplicated instance
   across your source files.

3. **Maintenance:** When optimizing algorithms or updating API calls,
   the changes automatically propagate to every part of the application that calls `m1`.

4. **Sharing:** The function can be exposed via header files, allowing entirely
   different modules to execute the routine.

## Core Function Terminology

```c
// ==========================================
// 1. Function defination
// ==========================================
/*
   This is the actual implementation or body of the function.
   When the compiler processes this, it generates the machine instructions and
   places them into the Code Segment (CS) of memory.
*/
int sum(int a, int b) {
    return a + b;
}

// ==========================================
// 2. Function calling / Function invoking
// ==========================================
/*
   The moment in the code where the CPU pauses its current sequence, pushes
   its current state onto the Stack, and jumps to the function's memory address
   to execute it.
*/
int result = sum(10, 20);

// ==========================================
// 3. Function declaration
// ==========================================
/*
   Often called a function prototype. It explicitly tells the compiler about the
   function's existence (its name, return type, and parameters) before the
   compiler actually sees the definition.
*/
int sum(int a, int b);

// ==========================================
// 4. Function declarator
// ==========================================
/*
   The specific syntactic component that introduces the function's identifier and
   parameter list. It is the core part of both the declaration and the definition.
   In `int sum(int a, int b)`, the declarator specifically is `sum(int a, int b)`.
*/
```

- Function definition: Definition will always has curly brace
- Function call: Call will always has semi colon

## Function Definitions, Compilation, and Execution Flow

```c
#include <stdio.h>

// ==========================================
// test() fn. defination (or) test() fn.
// ==========================================
void test() {
    printf("hello test");
}

// ==========================================
// main() fn defination (or) main() fn.
// ==========================================
int main() {

    // fn. calling / fn. invoking
    test();

    return 0;
}

```

This directly maps the terminology from the previous diagram into actual code, while
highlighting the most critical distinction in C programming: the difference between the
compiler's path and the CPU's path.

1. **`Compiling -> top to Botton`**. The compiler reads your `.c` file sequentially
   from line 1 downwards. Because `test()` is defined _above_ `main()`, the compiler
   already knows what `test()` is by the time it reaches the invocation inside `main()`.

2. **`Execution -> is from main()`**. Regardless of where `main()` is physically
   located in the file, the operating system (or runtime environment on a microcontroller)
   will always start the actual execution of the program at the entry point of `main()`.

Structural block diagram to visualize the execution flow:

```text
  main()         test()
 +--------+    +--------+
 |        |--->|        |
 |        |<---|   X    |
 +--------+    +--------+

 o/p: hello test

```

- Control jumps from `main()` up to the `test()` definition, executes the `printf`, and then
  returns back to `main()`.

- The 'X' drawn through the `test()` box is a crucial detail. It represents that once the
  function finishes executing, its memory footprint (its Stack frame) is immediately destroyed
  and released.

## Nested Function Calls and Stack Frame Destruction

```c
#include <stdio.h>

// ==========================================
// 3. The Deepest Nested Call
// ==========================================
void f2() {
    printf("I am in f2\n");
}

// ==========================================
// 2. The Intermediate Function
// ==========================================
void f1() {
    printf("I am in f1\n");

    // Control pauses here and jumps to f2
    f2();
    // Control returns here after f2 finishes

    printf("I am back to f1\n");
}

// ==========================================
// 1. The Entry Point
// ==========================================
int main() {
    printf("I am in main\n");

    // Control pauses here and jumps to f1
    f1();
    // Control returns here after f1 finishes

    printf("I am back to main\n");
    return 0;
}

/*
Output generated on the board:
I am in main
I am in f1
I am in f2
I am back to f1
I am back to main
*/

```

The above example illustrates exactly how this execution flow manipulates the Stack memory
segment in real time.

```text
  main()             f1()
 +--------+        +--------+
 |        | -----> |        |
 |   X    | <----- |   X    |
 +--------+        +--------+
                       |   ^
                       v   |
                   +--------+
                   |        |
                   |   X    |
                   +--------+
                     f2()

```

This nested box diagram demonstrates the Last-In, First-Out (LIFO) nature of the Call Stack.

- When `main` calls `f1`, `main`'s execution pauses.
- When `f1` calls `f2`, `f1`'s execution pauses.
- When `f2` completes, its memory frame is destroyed (represented by the 'X'). Control returns to `f1`.
- When `f1` completes, its frame is destroyed (the next 'X'). Control returns to `main`.
- Finally, `main` completes and is destroyed.

In the context of the embedded development you do with FreeRTOS or Zephyr, this exact mechanism
dictates how much Stack space you must allocate when creating a task. If your task calls a HAL
function, which calls an I2C driver, which calls a low-level register write, the Stack must be
large enough to hold all of those nested frames simultaneously without overflowing into the
Heap or Data segments.

Those 'X' marks are the final piece of the puzzle. When a function's frame is destroyed, every
local variable inside it is destroyed along with it.

## Arguments, Pass-by-Value, and Implicit Casting

```c
#include <stdio.h>

// ==========================================
// 1. Function Definition & Parameters
// ==========================================
void test(int i, float f) {
    printf("%d %f", i, f);
}

int main() {
    // ==========================================
    // 2. Variable Initialization in main()
    // ==========================================
    int x = 5;
    float y = 5.5;

    // 'x' and 'y' in the call as "Arguments"
    test(x, y);

    // ==========================================
    // 3. Syntax Error Cases
    // ==========================================
    test(5, 5.5); // Outputs: 5 5.5
    test( , 5.5); // C.E (Compile Error)
    test( , );    // C.E (Compile Error)

    // ==========================================
    // 4. Implicit Type Casting & Execution Cases
    // ==========================================

    // Integer to Float casting:
    test(5, 5);       // Outputs: 5 5.0

    // Float to Integer truncation:
    test(5.5, 5.5);   // Outputs: 5 5.5
    test(5.5, 5);     // Outputs: 5 5.0

    // Char to Integer/Float casting (ASCII conversion):
    test('a', 'b');   // Outputs: 97 98.0

    // Integer Division vs Float Division:
    test(5/2, 5/2);     // 2, 2 evaluates to: 2 2.0
    test(5.0/2, 5.0/2); // Evaluates to: 2 2.5

    // ==========================================
    // 5. Parameter Count Errors
    // ==========================================
    test(10);           // C.E: too few parameters
    test();             // C.E: too few parameters
    test(10, 3.75, 5);  // C.E: Extra Parameter
    test(10, );         // C.E: ES (Expected Semicolon / Expression Syntax)

    return 0;
}
```

The below diagram illustrates what happens in the Stack memory during a "Pass-by-Value"
function call.

```text
  main()
 +--------------------------+
 |   x            y         |
 | +---+        +-----+     |
 | | 5 |        | 5.5 |     |
 | +---+        +-----+     |
 +---|------------|---------+
     |            |
     v            v
 +---|------------|---------+
 | +---+        +-----+   X |
 | | 5 |        | 5.5 |     |
 | +---+        +-----+     |
 |   i            f         |
 +--------------------------+
  test()

```

When `main()` calls `test(x, y)`, it does not pass the actual variables `x` and `y`.
Instead, the CPU reads the values (`5` and `5.5`) and physically copies them into the newly
created Stack frame for `test()`, assigning them to the local parameter variables `i` and
`f`.

This is why modifying `i` or `f` inside `test()` does absolutely nothing to `x` or `y` in
`main()`. They are completely independent memory locations. And just like the previous, the
`test()` box has a large "X" through it. The moment `test()` finishes executing,
`i` and `f` are completely destroyed.

## Function Return Types and Return by Value

```c
#include <stdio.h>

// ==========================================
// 1. Returning a Value
// ==========================================
int test() {
    int a;
    a = 5;
    return a;
}

// ==========================================
// 2. Receiving the Returned Value
// ==========================================
int main() {
    int k;

    k = test();

    printf("%d", k);
    return 0;
}

```

Here is the precise architectural diagram illustrating the memory transfer before
the Stack frame is destroyed:

```text
  main()
 +-------------------------------+
 |     k                         |
 |   +----------+                |
 |   | ~~GV~~ 5 | <--------------|-------.
 |   +----------+                |       |
 +-------------------------------+       | 5
                                         |
 +-------------------------------+       |
 |     a                         |       |
 |   +----------+                |       |
 |   | ~~GV~~ 5 | ---------------|-------'
 |   +----------+                |
 +-------------------------------+
  test()

```

This diagram captures two critical concepts in C memory management.

First, the "GV" crossed out in both boxes stands for **Garbage Value**. When you declare
local variables like `int k;` or `int a;` on the Stack, the compiler does not zero them out.
They inherit whatever residual 1s and 0s were left in that physical memory address from
previous operations.

Second, Even though the `test()` Stack frame (and the physical variable `a` inside it) is
completely destroyed the moment the function finishes, the CPU copies the raw value of `a`
and passes it up to `main()` to overwrite the garbage value in `k`.

That crossed-out "GV" is the perfect transition point. By default, every local variable you
declare falls under the `auto` Storage Class, which is why it gets placed on the Stack and
initializes with a Garbage Value.

## Implicit Type Casting on Return Values

```c
#include <stdio.h>

// ==========================================
// 1. Float Truncated to Int
// ==========================================
int test1() {
    /*
       The function signature declares an 'int' return type.
       The board explicitly shows an arrow mapping 'return 3.75' to 'return 3'.
       The float is truncated before it ever leaves the function.
    */
    return 3.75;
}

void execute_case1() {
    float f;

    // The integer 3 is returned, then implicitly cast to 3.0 to fit float 'f'
    f = test1();

    printf("%f", f);                            // Outputs: 3.0
}

// ==========================================
// 2. Int Promoted to Float (Middle Board)
// ==========================================
float test2() {
    /*
       The signature declares a 'float' return type.
       The board notes 'return 30' (an integer), which the compiler automatically
       promotes to a float before returning.
    */
    return 3;
}

void execute_case2() {
    float f;

    f = test2();                                // Receives float 3.0 directly

    printf("%f", f);                            // Outputs: 3.0 (Board shows 3.0)
}

// ==========================================
// 3. Float Truncated on Assignment (Right Board)
// ==========================================
float test3() {
    return 3.75;
}

void execute_case3() {
    /*
       The board shows 'float f;' crossed out and replaced with 'int',
       along with '%f' crossed out and replaced with 'd'.
    */
    int f;

    // test3() successfully returns float 3.75.
    // However, the assignment operator forces it to fit into an integer variable,
    // truncating the decimal.
    f = test3();

    printf("%d", f);                            // Outputs: 3
}

```

The absolute rule demonstrated here is two-fold: the **function signature** is the ultimate
authority on what data format leaves the function's Stack frame, and the **receiving
variable's type** is the ultimate authority on how that data is stored in memory.

- Return type can be anything.
- Return value can be anything.
- Storing vatiable data type can be anything.

## The Syntax Rules of the return Statement

```c
#include <stdio.h>

// ==========================================
// 1. The Ternary Trap
// ==========================================
int test_invalid_ternary() {
    /*
       3>2 ? return 3 : return 2; // C.E (Compile Error)

       Why it fails: The ternary operator (?:) expects *expressions* that evaluate
       to a value. The 'return' keyword is a control flow *statement*, not an
       expression. You cannot embed a statement inside an operator.
    */
    return 0;
}

// ==========================================
// 2. The Arithmetic Trap
// ==========================================
int test_invalid_arithmetic() {
    /*
       return 10 + return 20; // C.E (Compile Error)

       Why it fails: You cannot perform arithmetic on the 'return' keyword itself.
       Once the CPU hits a 'return' statement, the function immediately terminates.
       It will never reach the second one anyway.
    */
    return 0;
}

// ==========================================
// 3. The Correct Implementations
// ==========================================
int test_valid_arithmetic() {
    // The expression evaluates first (10+20 evaluates to 30), then returns the result
    return (10 + 20);
}

int test_valid_ternary() {
    // It evaluates to 3, and then the return statement passes that 3 back to main.
    return (3 > 2 ? 3 : 2);
}

// ==========================================
// 4. Execution
// ==========================================
int main() {
    int a;

    // Capturing the correctly evaluated ternary return
    a = test_valid_ternary();

    printf("%d", a);                            // Outputs: 3
    return 0;
}
```

- Operator can be used in `return`. Eg. `return 10+30;`
- `return` should not be used with operator. Eg. `return 10 + return 30;`

## Nested Function Calls within Expressions

```c
#include <stdio.h>

// ==========================================
// 1. Base Function
// ==========================================
int f() {
    return 5;
}

// ==========================================
// 2. Nested Invocation
// ==========================================
int g() {
    // The CPU must pause g(), invoke f(), get the return value,
    // and then complete the addition.
    return 3 + f();
}

// ==========================================
// 3. Execution & Evaluation
// ==========================================
int main() {
    int a;

    // The compiler must evaluate both function calls before it can multiply.
    a = f() * g();

    printf("%d", a);

    // Evaluation Trace:
    // 1. f() evaluates to 5.
    // 2. g() is invoked. Inside g(), f() is invoked again, returning 5.
    // 3. g() completes its internal expression (3 + 5) and returns 8.
    // 4. The main expression becomes: a = 5 * 8;
    // 5. a is assigned 40.

    return 0;
}
```

## Return Type Mismatches and Compiler Warnings

```c
#include <stdio.h>

// ==========================================
// 1. Missing Return Value
// ==========================================
int test_missing_return() {
    /*
       The signature promises an 'int', but the statement is just 'return;'.
       This generates a specific compiler message:
       "Warning: fn should return a value"

       Because no specific value is provided, the function grabs whatever 1s and 0s
       happen to be sitting in the return register at that moment. So
       maps this to "return GV;" (Garbage Value).
    */
    return ;
}

void execute_left_case() {
    int a;

    // The Garbage Value (GV) is successfully assigned to 'a'
    a = test_missing_return();

    printf("%d", a);                            // Outputs: GV (Garbage Value)
}

// ==========================================
// 2. Void Function Returning a Value
// ==========================================
void test_void_return() {
    /*
       A 'void' function is allowed to use an empty 'return;' to exit early.
       However, attempting to return a physical value like 'return 5;'
       triggers a different message:
       "Warning: fn cannot return a value."
    */
    // return ;                                 // (Valid way to exit)

}

void execute_right_case() {
    int a;

       the compiler halts entirely.
       'a = test();' evaluates to 'a = ;'

       This triggers "C.E: ES" (Compile Error: Expression Syntax) because the
       assignment operator is missing its right-hand operand.
    */
    // a = test_void_return();

    // printf("%d", a);
}
```

## Operator Evaluation vs. Function Evaluation

```c
#include <stdio.h>

int test() {
    return 5;
}

int main() {
    int a;

    // ==========================================
    // 1. Operator Expression Evaluation
    // ==========================================
    /*
       Verbose: The compiler evaluates the expression '2+3', results in '5',
       and stores it in local variable 'a'.
    */
    a = 2 + 3;
    printf("%d", a);

    /*
       Inline: Storing is optional. The expression '2+3' is evaluated,
       and the resulting '5' is passed directly to printf.
    */
    printf("%d", 2 + 3);

    // ==========================================
    // 2. Function Call Evaluation
    // ==========================================
    /*
       Verbose: The CPU invokes test(), gets the return value '5',
       and stores it in local variable 'a'.
    */
    a = test();
    printf("%d", a);

    /*
       Inline: Storing is optional. The function test() is invoked,
       and the returned '5' is passed directly to printf.
    */
    printf("%d", test());

    return 0;
}
```

## Compiler-Dependent Argument Evaluation Order

```c
#include <stdio.h>

void test(int x, int y) {
    printf("%d %d ", x, y);
}

int main() {
    int a;
    a = 10;

    // ==========================================
    // The Sequence Trap: Multiple Increments in Arguments
    // ==========================================
    test(++a, a++);

    printf("%d", a);
    return 0;
}

```

This board highlights one of the most dangerous traps in C programming. When you pass arguments into a function, the C standard does not dictate which argument is evaluated first. The whiteboard explicitly traces both possible paths and labels the outcome as **"Compiler dependent"**.

Here is exactly how the board breaks down the two possible execution paths for `test(++a, a++)`:

**Path 1: Right-to-Left Evaluation (`<- R` on the board)**

1. The compiler evaluates the right argument `a++` first. Because it is post-increment, it passes the current value **10** to `y`, and then `a` becomes 11 in memory.

2. The compiler evaluates the left argument `++a`. Because it is pre-increment, `a` becomes 12 in memory, and it passes **12** to `x`.

3. `test()` prints `12 10`.

4. The final `printf` prints the updated variable: `12`.

5. **Output circled on board:** `12 10 12`

**Path 2: Left-to-Right Evaluation (`L -> R` on the board)**

1. The compiler evaluates the left argument `++a` first. `a` becomes 11 in memory, passing **11** to `x`.

2. The compiler evaluates the right argument `a++`. It passes the current value **11** to `y`, and then `a` becomes 12 in memory.

3. `test()` prints `11 11`.

4. The final `printf` prints the updated variable: `12`.

5. **Output circled on board:** `11 11 12`

The golden rule: **Never modify a variable multiple times inside the same function call or expression.**

## Compiler-Dependent Function Evaluation vs. Short-Circuiting

```c
#include <stdio.h>

// ==========================================
// 1. Function Definitions
// ==========================================
int f(int x) {
    printf("%d", x);
    return x;
}

int g(int y) {
    printf("%d", y);
    return y;
}

int main() {
    int a;

    // ==========================================
    // 2. The Arithmetic Operator Trap
    // ==========================================
    /*
       Just like function arguments, the order in which operands of an arithmetic
       operator (+) are evaluated is completely Compiler Dependent.
    */
    a = f(5) + g(3);
    printf("%d\n", a);

    // ==========================================
    // 3. The Logical Operator Exception
    // ==========================================
    /*
       Logical operators (|| and &&) are the exception to the rule.
       They enforce strict Left-to-Right evaluation to support short-circuiting.
    */
    a = f(5) || g(3);
    printf("%d", a);

    return 0;
}

```

For the arithmetic expression `a = f(5) + g(3);`, the board maps out two completely different valid execution paths:

- **Right-to-Left (`<-----`):** `g(3)` executes and prints `3`. Then `f(5)` executes and prints `5`. They return 3 and 5 respectively, which add to 8. The final `printf` outputs `8`. The total console output is `3 5 8`.

- **Left-to-Right (`----->`):** `f(5)` executes and prints `5`. Then `g(3)` executes and prints `3`. They add to 8. The final `printf` outputs `8`. The total console output is `5 3 8`.

This is another critical watch-out for cross-platform projects. Compiling this exact same arithmetic logic using the Texas Instruments compiler for a C2000 chip might yield `5 3 8`, while compiling it for an STM32 with GCC might yield `3 5 8`.

However, the board introduces `a = f(5) || g(3);` at the bottom right to show how logical operators solve this.

1. The `||` operator forces `f(5)` to execute first.
2. `f(5)` prints `5` to the console and returns `5`.
3. Because 5 is a non-zero (truthy) value, the logical OR expression is already satisfied. It **short-circuits**, meaning `g(3)` is completely ignored and never executes.
4. The result of the true OR expression is `1`, which is assigned to `a`.
5. The final `printf` outputs that `1`.
6. The total console output written at the bottom of the board is `51`.

## Conditional Execution using Logical Short-Circuiting

```c
#include <stdio.h>

void execute_short_circuit_logic(int a, int b, int n) {
    // ==========================================
    // 1. Relational Comparison
    // ==========================================
    /*
       Equivalent to: if (a > b) { printf("a is big"); } else { printf("b is big"); }

       MECHANICS EXPLANATION:
       This trick relies entirely on how && (AND) and || (OR) enforce left-to-right
       evaluation and short-circuiting.

       Scenario A (a > b is TRUE / Non-Zero):
       1. (True) && printf("a is big")
       2. The CPU must evaluate the right side of && to determine the final truth value.
       3. printf executes and returns the number of characters printed (a non-zero truthy int).
       4. The expression is now evaluating the OR: (True) || printf("b is big").
       5. Because the left side of || is True, it short-circuits. The second printf is skipped.

       Scenario B (a > b is FALSE / Zero):
       1. (False) && printf("a is big")
       2. The && operator immediately short-circuits. The first printf is completely skipped.
       3. The expression is now evaluating the OR: (False) || printf("b is big").
       4. Because the left side is False, the CPU is forced to evaluate the right side.
       5. The second printf executes.

       ASCII FLOW DIAGRAM:
       [ Condition Evaluated ]
                |
                +-- (True) ---> Executes Left printf ---> (Short-circuits ||) ---> Done
                |
                +-- (False) --> (Short-circuits &&) ----> Executes Right printf -> Done
    */
    a > b && printf("a is big") || printf("b is big");
    printf("\n");

    // ==========================================
    // 2. Modulo Arithmetic (Odd/Even)
    // ==========================================
    /*
       Equivalent to: if (n % 2 != 0) { printf("odd"); } else { printf("even"); }
       If n%2 yields a remainder (True), the left printf executes.
    */
    n % 2 && printf("odd") || printf("even");
    printf("\n");

    // ==========================================
    // 3. Sign Check (Positive/Negative)
    // ==========================================
    /*
       Equivalent to: if (n > 0) { printf("+ve"); } else { printf("-ve"); }
       If n>0 is True, the left printf executes.
    */
    n > 0 && printf("+ve") || printf("-ve");
    printf("\n");
}
```

While this is an excellent exercise in understanding compiler behavior, using logical operators
to replace `if-else` control flow violates strict embedded programming standards. In a
production environment like your MCU Bridge project, this syntax directly violates MISRA C
guidelines (specifically directives regarding expression side-effects and boolean conversions).

Control flow should always explicitly use control flow statements (`if`, `else`, `switch`) to
ensure deterministic CPU branching.

## Top-to-Bottom Compilation and Implicit Declarations

```c
#include <stdio.h>

// ==========================================
// 1. The Redeclaration Error
// ==========================================
/*
   ASCII FLOW DIAGRAM:
   [Top of File]
         |
         v
   void main() {
       show();  -------> Compiler has not seen show() yet.
   }                     It implicitly assumes the signature: `int show(int);`
         |
         v
   void show() { ------> ERROR: "C.E: redeclaration to show()"
       ...               Conflicts with the implicitly assumed `int` type.
   }

   CODE EXPLANATION:
   Because the C compiler processes code strictly from top to bottom, it hits
   the invocation of show() inside main() before knowing what show() actually is.
   Historically, the compiler defaults to assuming unknown functions return an 'int'
   and takes all are int arg. When it continues down the file and finds the actual
   definition starting with 'void', it throws a Compile Error (C.E.) because
   the types no longer match.
*/

// ==========================================
// 2. The Three Solutions
// ==========================================
/*
   To resolve this top-to-bottom compilation trap, you must guarantee the compiler
   knows the correct signature before the function is called. There are 3 solutions:

   Solution A: Keep the show() definition above main().
   Solution B: Change the return type of show() to 'int' so it matches the
               compiler's implicit assumption.
   Solution C: Provide a function prototype (declaration) before main() to establish
               the signature early, leaving the definition at the bottom.
*/

// ==========================================
// 3. Executing Solution A
// ==========================================
void show() {
    // The definition is placed at the top, so the compiler learns the 'void'
    // signature before main() is ever parsed.
    printf("hello show\n");
}

int main() {
    show();

    // Output written on board: hello show
    return 0;
}

```

In embedded systems development, relying on the compiler's implicit `int` assumption is highly
dangerous and explicitly forbidden by MISRA C standards. Modern embedded compilers for STM32 or
TI C2000 chips will immediately flag missing prototypes as severe errors rather than trying to
guess the return type.

For your project, "Solution C" (providing a prototype before `main`) is the architectural
standard. This is exactly why header (`.h`) files exist. By placing all your function
declarations (`void timer_init(void);`) into a header file and `#include`-ing it at the very
top of your `.c` files, you guarantee the compiler has a complete map of all function
signatures before it ever evaluates a single line of execution code.

### Solution C: Function Prototypes

```c
#include <stdio.h>

int main() {
    // ==========================================
    // 1. The Declaration (Prototype)
    // ==========================================
    /*
       The board circles this line and labels it: "-> declaration (Prototype/signature)"
       This is the implementation of "Solution C" from the previous board. By declaring
       the prototype early, it explicitly tells the compiler about test() before it is
       called, preventing the top-to-bottom compilation error.

       Notice that variable names are omitted in the prototype; only the data types
       (int, float) are required to establish the signature.
       But dummy names can also be provided like
       void test(int a, float b);
    */
    void test(int, float);

    int x = 5;
    float y = 5.5;

    test(x, y);
    return 0;
}

// ==========================================
// 2. The Function Definition & Declarator
// ==========================================
/*
   The board boxes the signature line `void test(int a, float b)` and labels it
   "-> fn. declaraton" (declarator).
   The entire block, including the body, is labeled "-> defination".
*/
void test(int a, float b) {
    printf("%d %f", a, b);
}

/*
   ASCII FLOW DIAGRAM (Call Stack):
   The board draws this diagram to visualize the data passing from main to test,
   with cyclical arrows representing the invocation and return.

     main()
    +-------------------+
    |   x         y     |
    | +---+     +-----+ |
    | | 5 |     | 5.5 | |
    | +---+     +-----+ |
    +-------------------+
      |               ^
      |               |
      v               |
    +-------------------+
    |   a         b     |
    | +---+     +-----+ |
    | | 5 |     | 5.5 | |
    | +---+     +-----+ |
    +-------------------+
     test()

   Output: 5 5.5
*/

```

In embedded systems programming, especially for a modular hardware abstraction layer like your MCU Bridge, placing prototypes inside `main()` is strongly discouraged. Instead, prototypes are extracted into dedicated header (`.h`) files (e.g., `gpio_hal.h`).

When you `#include` a header file, the preprocessor automatically pastes all of those prototypes at the very top of your `.c` file before the compiler even starts reading top-to-bottom. This ensures the compiler knows exactly how much stack memory to allocate or which hardware registers to use for parameter passing (e.g., knowing it must prepare a 32-bit floating-point register rather than a standard integer register) long before the function is ever actually called in the execution flow.

## Global vs. Local Function Declarations

```c
#include <stdio.h>

// ==========================================
// 1. The Global Declaration Solution
// ==========================================
/*
   The board introduces a 'Global declaration' placed at the very top of the
   file, outside of any specific function block.

   Because the C compiler reads top-to-bottom, declaring the prototype here
   ensures that every single function that follows it instantly recognizes
   the signature of f3().
*/
void f3(); // Global declaration

// ==========================================
// 2. Redundant Local Declarations
// ==========================================
/*
   The board draws a long line originating from the global declaration and
   strikes directly through the local declarations inside f1(), f2(), and main().
   This illustrates that while declaring prototypes locally inside a calling
   function is technically valid C syntax, it is highly redundant and unnecessary
   if a global declaration exists.
*/
void f1() {
    // void f3(); // Local declaration
    f3();
}

void f2() {
    // void f3(); // Local declaration
    f3();
}

void main() {
    // void f3(); // Local declaration
    f1(); f2(); f3();
}

// ==========================================
// 3. The Function Definition
// ==========================================
void f3() {
    printf("hello f3\n");
}

```

This global declaration mechanism is the exact foundational concept that makes header files
(`h`) work in embedded systems programming.

When you build project, you will never write local function declarations inside your hardware
abstraction layer files. Furthermore, you will rarely even write global declarations directly
in your `.c` files. Instead, you extract those global declarations into a dedicated header
file (like `system_rcc.h` for STM32 or `sysctl.h` for TI C2000) and use the `#include`
directive at the top of your `.c` files.

The preprocessor simply pastes those global declarations at the top of your compilation unit,
achieving the exact same top-down visibility shown on the whiteboard while keeping your source
files clean and modular. Strict standards like MISRA C explicitly forbid local function
prototypes to ensure all module interfaces are managed globally through headers.
